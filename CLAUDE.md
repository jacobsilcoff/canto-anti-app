# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A self-hosted multi-user Anki-style spaced repetition (SRS) flashcard app for language learning. Users translate words/phrases via Gemini AI and study them with SM-2 scheduling. Deployed on Oracle Cloud Free Tier via Docker + Caddy.

**Deployment:** `git push` is all that's needed — the server auto-deploys on push. Do NOT SSH in manually to pull/rebuild.

- **`main`** auto-deploys to **production**. Nothing else does.
- **Any non-`main` branch push deploys to the dev site** `dev.canto-ank.silcoff-labs.ca` (`.github/workflows/deploy-staging.yml` is `branches-ignore: [main]` — it checks out the pushed branch and rebuilds, so the dev site reflects the **last** non-main branch pushed).
- **Work on a feature branch, then merge it to `main`.** That is the actual workflow — recent history is `claude/<topic>` branches merged straight into `main`, and each of those pushes exercised the dev site on the way. Do NOT commit directly on `main`.
- **`develop` is dormant, not canonical.** It carries no commits of its own (identical to an older `main`) and is kept only because the staging workflow predates the current flow. Don't branch from it — branch from `main`, or you start behind. If it ever gets used again, fast-forward it to `main` first.
- **Checking what's deployed:** `GET /api/version` (no auth) → `{commit, branch, built_at, asset_version, environment}`, also shown in the Settings footer. `asset_version` is a **static-content hash** — it only changes when a file under `static/` changes, so a backend-only deploy leaves it identical; use `commit`/`built_at` to confirm a backend deploy landed.

SSH to production (only if debugging): `ssh -i ssh-key-2026-05-26.key ubuntu@40.233.111.173`

## Architecture

**Stack:** FastAPI + aiosqlite (backend), SQLite (data), Gemini 2.5 Flash Lite (translation), edge-tts (audio), Vanilla JS (frontend), Caddy (reverse proxy + HTTPS).

### Layer overview

| File | Role |
|------|------|
| `main.py` | All FastAPI routes, auth middleware, session management |
| `db.py` | All DB access — schema, migrations, CRUD. Every function takes `user_id` for isolation |
| `translation.py` | Gemini prompt construction, JSON parsing, retry logic; `LANG_INFO` + `SCRIPT_BY_LANG` language registry |
| `audio.py` | edge-tts wrapper; returns MP3 bytes; `VOICES` map. `generate()` **retries** (`_ATTEMPTS`=3, backoff, `_TIMEOUT_S`=20 per try) and **never returns `b""`** — edge-tts is a free unofficial Microsoft endpoint that throttles and drops sockets, and some versions end an empty stream without raising, which would be stored as the card's audio and play as silence forever. Raises on total failure so callers decide what a silent card looks like |
| `srs.py` | SM-2 with sub-day learning steps; pure/stateless — takes card state, returns new state |
| `tokenizer.py` | Reader word-segmentation (CJK via jieba/pycantonese, Thai via pythainlp, else alphabetic regex incl. Devanagari/Telugu/Hangul) + offline romanization for ruby. `split_sentences(tokens, lang)` splits on sentence-ending punctuation, with per-language extras: Thai splits on spaces (no sentence punctuation), Greek treats `;`/U+037E as the question mark. `script_class(text)` (`"native"`/`"latin"`/`""`) is the language-agnostic script oracle behind drill option hygiene |
| `auth.py` | scrypt password hashing + timing-safe verification |
| `learning.py` | AI Learning Path — just-in-time `plan_next_lesson` (picks the next skill + breadth from live state) + unified `author_lesson` (teach blocks + drills together) + deterministic drill assembly/validation. Both LLM calls route through `llm.call` (provider-pluggable) |
| `llm.py` | Provider dispatcher for the lesson pipeline — `call(prompt, *, model, gemini_key, anthropic_key)` routes `claude-*` models to the Anthropic SDK (server-side shared key), everything else to `translation._call` (Gemini). Reuses `translation._parse_json`. The A/B switch for lesson-model quality |
| `tutor.py` | Tutor chat — one single-prompt LLM call per learner message (history serialized in) + strict normalization of the structured reply (corrections / new_items / points); romanization always recomputed by the offline oracle. Construction drills tier vocab by deck size + verify-then-snap (`start_drill`) |
| `embeddings.py` | Pure Gemini text-embedding wrapper (`gemini-embedding-001`, 768-dim) — `embed`, `cosine`, `nearest`, `pack`/`unpack`. No DB (caching orchestrated by callers). Powers the tutor's known-vocab snapping |
| `grammar.py` | Reliable verb conjugation engine (French present) — rules + curated irregulars; an independent oracle, never trusts the LLM |
| `grammar_lessons.py` | Legacy per-concept grammar generator (shared `concept_content` cache); **no longer called by the lesson route** — `learning.py` reuses its block/cloze helpers + `GENERATION_MODEL`. Also the home of the shared **option-hygiene** guards (`_norm`, `drop_cross_script`, `drop_homophones`) used by both its own `_clean_block`/`_free_cloze` and `learning._assemble_drill` — they live here because `learning` imports `grammar_lessons`, not the reverse |
| `foundations.py` | Curated **reading** track for non-Latin scripts — deterministic, no LLM. Per-script-type engines: Hangul jamo (Korean) + abugida (Hindi/Telugu). `build_units()` returns pre-built course units; wired into course creation as a **skippable** prepended track |
| `extract.py` | Reader URL/PDF import — deterministic, no LLM. `fetch_and_extract_url` (SSRF-guarded `httpx` fetch + trafilatura article extraction), `extract_pdf` (pypdf text), `clean_text`. Returns `{title, text}`; raises `ExtractError` (→ 4xx) on user-fixable failures. Heavy parsers imported lazily. Also hosts the **vision re-extraction** helpers used by the textbook pipeline: `render_pdf_pages` (rasterize pages to JPEG via `pypdfium2`, from bytes or a path, per-page best-effort) + `pdf_page_count`, `page_text_quality`/`assess_page_quality`/`native_script_ratio` (heuristic that flags garbled/scanned/romanization-only extractions and, for a non-Latin target language, a book with almost no native script) |
| `even-glasses/` | **Even Hub plugin** for Even Realities G2 smart glasses — a Vite + TypeScript web app using `@evenrealities/even_hub_sdk`. Reviews due flashcards on the glasses HUD via the site's REST API (bearer-token auth). `src/api.ts` = REST client (`dueSession(labelIds?)` scopes to a deck via the existing `label_ids` filter, `listLabels()` for the picker), `src/cards.ts` = pure display logic (which faces are playable, prompt/answer), `src/glyph.ts` = big-glyph rasterization (`shouldRenderAsGlyph` pure/tested + `renderGlyph` canvas→grayscale bitmap), `src/config.ts` = localStorage config, `src/main.ts` = Even Hub bridge + review loop. **Phone side:** setup is **token-first** — the site URL defaults (`config.DEFAULT_BASE_URL`, now the **prod** site — the plugin's CORS middleware shipped to `main`) behind an "Advanced" line, so a user just pastes a token. Once connected, a persistent phone **deck panel** picks a deck/label to study (📦 deck labels first) and (re)starts the review; the choice persists (`canto_deck_labels`) and glasses-only launches reuse it. **Glasses controls:** prompt — tap = reveal, **double-tap = go back** (re-show previous card, navigational only — re-grades, no server-side grade reversal); reveal — tap/swipe-up = good, double-tap/swipe-down = again. Every grade shows a brief **👍/👎 confirmation** (finicky-ring feedback). Short single-word prompts (≤`glyph.MAX_GLYPH_CHARS`=4 code points, no internal whitespace) are drawn **large + centered** via the SDK **image path** (`renderGlyph` auto-shrinks the font to fit, so longer would render but stops being a legibility win) (`ImageContainerProperty` + `updateImageRawData`, gray4 ≤288×144) — **best-effort with text fallback** (the exact gray4 wire format is undocumented and needs on-device verification; any failure degrades to text). No true binocular depth (SDK exposes one 2-D container space). Non-Latin shows romanization; Latin pronunciation faces skipped (no speaker). **No server changes** — `/api/cards/due` already accepts `label_ids` and `/api/labels` is bearer-auth reachable. Server-side: `api_tokens` table (migration 040), bearer auth in `auth_middleware`, generate/revoke routes at `/api/profile/api-token`, settings UI in `static/settings.html` |

### Database schema

- **cards** — source_text, target_text, romanization, target_lang, audio_data (BLOB), notes, priority (1–5), tutor_flag, suspended
- **card_faces** — one row per face per card (`source`, `target`, `pronunciation`); each face has independent SM-2 state (next_review, interval_days, ease_factor, repetitions, first_seen_date, learning_step). `learning_step` non-NULL = card is in (re)learning with sub-day steps; NULL = graduated review card.
- **labels / card_labels** — per-user tags; many-to-many with cards
- **users** — scrypt-hashed passwords, is_admin flag, `avatar_media_id` (migration 036) → a `media` record (UUID hex) for the user's profile picture. Uploaded via `POST /api/profile/avatar` (center-crop to square + resize to 400px, JPEG, stored with `conv_id=NULL`), cleared via `DELETE /api/profile/avatar`; both delete the previous file. Exposed as `avatar_url` (`/api/media/{id}.jpg`) from `/api/me`, `/api/profile`, `db.list_conversations`, `db.get_friends`, `db.get_weekly_league`, and the friends-search/leaderboard routes — i.e. everywhere another user's identity is shown. Rendered as an `<img>` (falling back to initials) inside: chat's `.msg-conv-avatar`/`.msg-chat-avatar` and the friends-modal/leaderboard's `.mini-avatar` (`messages.html`), and the Learn-page weekly league strip/sheet's colored-initial circles (`learn.html`'s `_avatarInner`, swapped in over the deterministic `_avColor` fallback). The Home greeting (`today.html`) uses the user's **first name** (split from `display_name`); `/api/me` now returns `display_name` (previously it didn't, so the greeting silently fell back to username).
- **user_settings** — key-value store (new_cards_per_day, default_target_lang, learner_profile, chat_compact_phrases, lesson_length, lesson_ai_speak, lesson_warmup, speaking_drills, audio_mix, audio_volume, sfx_volume, daily_xp_goal, course_focus, `timezone` (IANA name — see *Per-user day boundaries*), `streak_freezes`/`streak_freeze_progress`/`streak_freeze_used_date` (B5 streak freeze), `lesson_feedback` (D4 · JSON ring buffer of 👍/👎 signals the planner quotes), …)
- **courses / course_units / course_lessons / course_concepts** — per-user AI Learning Path. `courses.active_plan` = JSON of the **in-progress chapter** (`{title, objective, summary, budget}`), NULL between chapters. `budget` = the chapter's planned lesson count (2–6 for AI-planned units; reviewed textbook units may contain 1–12); `summary` is a **running roll-up** of each authored lesson's summary (`learning.roll_chapter_summary`, capped) so the planner sees progress toward the objective. (No longer a frozen concept list + cursor — the planner re-decides each lesson; a stale old-format plan is ignored and overwritten on next generation.) `db.get_course` also returns `active_chapter` (`{title, budget, lessons_done}`) and `queued_lessons` for the roadmap. `course_lessons.content` = the authored `{segments:[...]}` (set at creation, since lessons are authored one at a time). `course_lessons.crown_level` (0–3, migration 018) = the skill-tree crown, bumped per completion. Units still close reactively (`close_unit` back-assigns `unit_id` when the planner opens a new chapter). `course_concepts` registers the skill + the vocab items actually taught. `course_units.theme` = `'foundations'` marks pre-built reading units, `'textbook'` marks a textbook unit (its lessons are authored via the unit-scoped `_author_textbook_lesson` and attached directly, so `get_course` gives textbook units their **own** availability cursor + a `queued_remaining` count — see lesson_queue), else `''` (AI-planned). `course_units.textbook_id`/`chapter_idx` (migration 044) record **which chapter of which book** a textbook unit came from; the link used to live only on `lesson_queue` rows, which are deleted as lessons are authored, so a fully-generated unit couldn't be found by chapter. That link is what makes ONE unit per chapter enforceable (`db.get_textbook_units` → `GET /api/textbooks/{id}/units`), lets `get_course` order textbook units by the **book's** chapter order (not build order, so reading a book out of order still lists it the way the book reads), and survives a merge (`db.collapse_unit_chapter_idx` re-points units when a boundary is deleted). `db.get_course` also returns each textbook unit's `queued` list (`[{id, idx, title}]` from the still-queued specs) so the Learn page can **reserve a row per un-authored lesson** instead of showing a bare counter, plus `book_title`. Deleting a book NULLs the link but keeps the units (their lessons are the learner's). `db.delete_course_unit` / `db.delete_lesson` (→ `DELETE /api/course-units/{id}` / `DELETE /api/lessons/{id}`) drop a unit or a single lesson together with the `course_concepts` rows it introduced; mastery history is deliberately kept (it describes the learner, not the lesson). `db.get_unit_next_lesson` powers the results screen's "Next lesson →". `db.get_course` still returns `queued_lessons` (legacy course-wide count) for compatibility, but the Learn page no longer surfaces it as a global banner.
- **concept_mastery** — `(user_id, lang, concept_key, correct, total, last_seen)`. Incremented each time the learner completes a lesson (first-pass drill outcomes only). Fed back to the unit planner: weak concepts (≥3 attempts, <70% accuracy) are surfaced in the prompt so the planner can weave in extra practice.
- **concept_content** — `(lang, concept_key)` → legacy shared grammar artifact; **retained but unused** by the new lesson path.
- **tutor_conversations / tutor_messages** — per-user, per-language tutor chats. User turns store plain text; tutor turns store the structured JSON payload (`{reply, corrections, new_items, points}`). The first user message becomes the conversation title.
- **points_ledger** — `(user_id, lang, points, reason, created_at)`, append-only light gamification. Lifetime total + **today's XP** surface in `GET /api/streak` (`points`, `points_today`, `daily_goal`, plus `streak_freezes` + `streak_freeze_used_date` for the B5 shield) — the header pill ("🔥 N · 🛡 · ⭐ M") and the Home/Learn daily-goal XP rings. Lessons award XP (reason `'lesson'`) on their FIRST completion only (`db.complete_lesson` returns `(found, first)`; `complete_lesson` route clamps client-reported `xp` ≤ `_MAX_LESSON_XP`=300). Other reasons: `'review'` (SRS good/easy answers), `'quest'` (daily-quest chest, 20–40 deterministic), `'checkpoint'` (unit checkpoint first pass, +40). `daily_goal` is the **`daily_xp_goal` user setting** (10/30/50/100 picker in Settings, clamped 10–200 via `main._daily_goal`; default 50). **`/api/streak` is network-first in the service worker** (`static/sw.js` `NETWORK_FIRST_API`, not the SWR set) — it changes on every review/lesson/tutor turn, so serving a stale cached hit made the Home ring look stuck. The Home ring is also resilient offline: `static/cards.html` mirrors each flashcard review's XP award into a same-**local**-day `localStorage` counter (`xpLocalToday`) immediately, whether the review synced online or is queued offline; `static/today.html` renders `max(serverPointsToday, xpLocalToday)` and caches the last `/api/streak` response (`streakCache`) as an offline fallback, so the ring updates instantly from local practice and still shows something with no connection. Both pages key those caches by `_localDateStr()` — which must stay in step with the server's local-day window in `db.get_points_today`.
- **daily_quests** — `(user_id, quest_date, quest_key, target, progress, claimed)`, UNIQUE per user+day+key (migration 035). 3 rotating quests/day seeded lazily by `db.get_daily_quests` (`earn_xp` always + 2 deterministic picks from `db.QUEST_TEMPLATES` via a user+date hash — `db.quest_keys_for`). `earn_xp` progress is re-derived from `points_ledger` on every read; other quests advance via `db.bump_quest` at event sites (lesson complete / perfect, card create, SRS review, tutor turn) or, for client-only signals (best combo, listening hits, **lightning-round completion** (B4)), via `POST /api/quests/progress` (keys allowlisted in `db.CLIENT_QUEST_KEYS`, clamped). All 3 done → the chest is claimable once (`POST /api/quests/claim` → `db.claim_daily_chest`, deterministic 20–40 XP, reason `'quest'`). Surfaced as a quest card on the Learn page, a compact strip on Home, and quest ticks on the lesson results screen.
- **lesson_queue** — `(course_id, idx, unit_title, unit_size, spec_json, source, textbook_id, chapter_idx, unit_id)` (migrations 037/038/042). Holds a textbook unit's not-yet-authored lesson specs. `unit_id` (migration 042) **scopes each queued row to a `theme='textbook'` `course_units` row** — the AI path (`_author_next_lesson`) NO LONGER peeks the queue; a dedicated `main._author_textbook_lesson` (via `POST /api/course-units/{id}/next-lesson`) consumes rows for ONE unit, grounding the author in verified source excerpts and attaching the lesson directly to that unit (bypassing `active_plan`/`close_unit`). So textbook lessons never interleave into the AI course path. `db.peek_lesson_queue_for_unit`/`count_lesson_queue_for_unit`/`clear_lesson_queue_for_unit` are the unit-scoped helpers. A reviewed textbook chapter (`POST /api/textbooks/{id}/unit`) creates the unit row up front, queues its complete 1–12 lesson plan, and authors lesson one immediately; the rest are authored from the "📕 From your textbooks" section on Learn — **one at a time, all at once ("⚡ Build all N remaining", a client-side loop over the same route so each lesson appears as it lands and no single request can time out), or ahead of you**: `main._prefetch_textbook_lesson` is a background task fired after unit creation and after each textbook-lesson completion, so the next lesson is usually already built by the time you reach it (best-effort — quota, errors and races are swallowed since nothing waits on it). `POST /api/course-units/{id}/next-lesson` returns `queued_remaining` so the "build all" loop knows when to stop. Migration 042 **adopts any legacy in-flight batches** into textbook units so removing the AI-path consumption strands nothing. Cleared on course delete / "Restart course" / per-unit `DELETE /api/course-units/{id}/queue`.
- **textbooks** — `(user_id, course_id, title, filename, num_pages, pages_json, chapters_json, images_json, pdf_media_id, last_page, bookmarks_json)` (migrations 038/039/041/043). Each uploaded PDF persists a user-editable title, per-page cleaned text, editable detected units, and metadata for useful embedded raster images stored through the existing `media` system. Users may correct the unit ranges, choose custom pages, edit extracted text, and approve up to six page-linked visuals before unit generation. `pdf_media_id` (migration 041) keeps the **original PDF file** (`{id}.pdf` in `MEDIA_DIR`) so any page range can be re-rendered on demand for **AI vision re-extraction** (see Textbook units) AND for the **chapter reader's lazy page images** (`GET /api/textbooks/{id}/page/{n}.jpg` → `extract.render_pdf_pages`, cached to `MEDIA_DIR/tbpage_{id}_{n}.jpg`; 409 for books with no stored PDF, which read text-only). Renders are bounded by `_TEXTBOOK_RENDER_SEM` (2 at a time), read straight off the stored file (`extract.render_pdf_pages` accepts a path, so a 25 MB book isn't copied into RAM per page request), and are cached **atomically** — a truncated cache file (`< _MIN_PAGE_JPEG_BYTES`) is treated as absent and re-rendered instead of being served as a broken image forever, and a failed cache write (full disk) still serves the render. `GET /api/textbooks/{id}/reader` reports `renderable_pages` (`extract.pdf_page_count`): when a damaged PDF rasterizes fewer pages than text extraction produced, the reader says so up front and shows those pages' extracted text instead of firing image requests that can only fail; **`0` means nothing rasterizes** and the whole book reads as text (the client must not `||`-fallback that 0 to `num_pages`). **PDF repair (`extract.repair_pdf`)** — pypdf finds the `%PDF-` header at ANY offset and rebuilds a broken xref by scanning for objects; pdfium checks only the start of the file and refuses with `Data format error`. So a book can extract every page of its text — proving we parsed it — and rasterize *nothing*, which reads as the reader being broken. `repair_pdf` tries the cheap byte-preserving fix first (drop leading junk before the header, keeping page geometry and the xref valid), then re-serializes the parsed document via pypdf (fresh xref + trailer, which also recovers a corrupt one), **verifying each candidate against the rasterizer** before returning it. It runs at upload (`extract.can_render` gate → the stored file is already repaired, and `can_transcribe` reflects it) and lazily on open via `main._ensure_renderable_pdf`, which replaces the stored file atomically (`_replace_stored_pdf`) — so books uploaded before this existed heal on their next open, and the page-image route repairs-and-retries too (the library cover requests page 1 before anything opens the reader). `extract.RendererUnavailable` (an `ExtractError` subclass) keeps "no rasterizer on this server" distinct from "this book won't open": the former is a server gap, so it must never trigger a repair or mark a good book unrenderable — `_ensure_renderable_pdf` returns its optimistic `fallback` instead. Failed repairs are remembered in `main._unrepairable_pdfs` so every page request doesn't re-attempt a whole-file rewrite. `last_page`/`bookmarks_json` (migration 043) are the reader's per-book resume point + bookmarked pages, updated via `PUT /api/textbooks/{id}/reading` (`db.set_textbook_reading`); `db.get_textbook`/`list_textbooks` expose `last_page`, `bookmarks`, and `has_pdf`. `db.update_textbook_pages` overwrites `pages_json` (and `num_pages`) with the cleaned transcripts; book/course deletion unlinks the stored PDF + the `tbpage_*` cache alongside the page visuals.
- **course_units.checkpoint_passed / checkpoint_score** — (migration 035) unit checkpoint quiz state. A closed AI unit's path segment ends in a 🛡 **Checkpoint node**: `GET /api/units/{id}/checkpoint` assembles a drills-only quiz (8–10 questions sampled deterministically from the unit's lessons' STORED drills — hardest kinds preferred (reorder → cloze → production → listening → recognition → match), seeded by unit id, `construction_drill`/mini-games excluded; no LLM). `POST` records the attempt (`db.record_checkpoint` — best score kept, passed sticky): pass ≥80% → gold shield on the node + one-time +40 XP + mastery-ledger bumps. The node unlocks when every lesson in the unit is done.
- **study_activity** — `(user_id, study_date)`, one row per active day; drives `get_streak`. Recorded by `db.record_study_activity` on ANY meaningful activity — an SRS review, completing a lesson, OR a tutor turn — so the streak reflects all study (not only flashcard reviews; previously tutor/lesson use earned ⭐ but silently let the 🔥 streak lapse). The header pill (`loadStreak`) is loaded on every page including Learn.
  - **`study_date` is the learner's LOCAL day** (see *Per-user day boundaries* below), not UTC.
  - **Every write goes through `db._mark_study_day(conn, user_id, day=None)`** — it resolves the local day, inserts the row, and bridges any freezable gap, all on the caller's open connection. `record_study_activity`, `add_points`, `apply_card_review` and `update_face_review` all funnel through it, so the streak can never depend on which request arrived first. `day` **backdates** the row: `POST /api/cards/{id}/review` accepts `studied_on` (validated by `main._clamp_studied_on` — must parse, not be in the future, not older than `_MAX_BACKDATE_DAYS`=7, else ignored), so an offline review queued in IndexedDB and synced days later still counts for the day it was answered instead of the day it synced.
  - **`db.get_streak` is PURE** — it never writes. Freeze consumption lives in `db.apply_streak_freezes(user_id)`, called from the `/api/streak` route (owner's own read) and implicitly from every study write. This is what makes rendering a friend's streak on `/api/friends/leaderboard` safe; it used to spend *their* shields and fabricate activity rows on *their* account as a side effect of someone else opening a screen.
  - **Streak freeze (B5):** `db._bridge_streak_gap` looks only at activity **strictly before today**, so bridging is order-independent (the old rule required the most recent activity to be exactly `today - 2`, so a review landing before any `/api/streak` call hid the gap and reset the streak with the shield unspent — an invisible race). It fills gaps of **any** width the learner can afford, **all-or-nothing** (a part-filled gap still breaks the streak, so unaffordable gaps leave the shields banked), and skips gaps whose prior streak is under `STREAK_FREEZE_MIN_STREAK`=2. Per-day `INSERT OR IGNORE` with a rowcount-gated decrement keeps it idempotent under concurrency. Freezes are earned, not bought: `db.earn_streak_freeze` grants one per `STREAK_FREEZE_PER_LESSONS`=10 first-completions, capped at `STREAK_FREEZE_CAP`=2 (called from `complete_lesson`; the route returns `freeze_earned`). `/api/streak` returns `streak_freezes` + `streak_freeze_used_date`; `renderHeaderStats` shows a 🛡 shield pill and `learn.html` toasts on earn/consume (comparing `used_date` against the **local** yesterday).
  - `db.set_streak` (admin override) reshapes history destructively; `db.ensure_min_streak(user_id, days)` is the **insert-only** sibling used when a timezone change would otherwise shorten an earned streak.
- **embedding_cache** — `(lang, model, word)` → packed float32 `vector` BLOB. Shared across users (a word embeds the same for everyone). Populated lazily as the tutor needs known-word vectors for construction-drill snapping; `db.get_cached_embeddings` / `put_cached_embeddings` (pack/unpack live in `embeddings.py`).
- **api_tokens** — `(token_hash TEXT PK, user_id, label, created_at)`. Long-lived bearer tokens for programmatic API access (the Even glasses plugin). Only `sha256(token)` is stored (like sessions). One active token per user — regenerating replaces the old one. Routes: `POST /api/profile/api-token` (mint), `DELETE /api/profile/api-token` (revoke). Auth middleware checks `Authorization: Bearer <token>` when no session cookie is present. **CORS:** the plugin is a cross-origin web app (Even Hub CDN / Vite dev server), so `main.py` registers `CORSMiddleware` (`allow_origins=["*"]`, `allow_credentials=False` — the plugin auths with a Bearer token, never a cookie) as the OUTERMOST middleware so the browser's preflight `OPTIONS` is answered before `auth_middleware` 401s it. Without this every plugin `fetch` is silently blocked by the browser (symptom: the glasses hang on "Loading your flashcards…").
- **feedback** — `(user_id, type, title, description, screenshot_media_id, status, priority, triage_summary, triage_group, suggested_prompt, admin_notes)`. Bug reports and feature requests submitted by users. AI-triaged on submission via `translation.triage_feedback` (assigns priority, groups similar reports, generates a suggested Claude Code prompt for fixes). The Labels tab also has a **search input** to filter labels by name. Each label row has a **Populate** button (`POST /api/labels/populate` → `translation.suggest_vocab_for_label`) that asks flash-lite to generate practical vocab for the category (e.g. "adjective" → common adjectives). **Token-lean & deck-aware:** the LLM is fed ONLY the words already under that label (`db.get_label_words`, newest 40) — not the whole deck — so it matches the label's granularity/style and avoids repeats. Each suggestion is then routed against the deck (`db.match_cards_by_target`, exact target match + label-membership check): words already in the deck but NOT under this label come back as an **"Already in your deck — tag with this label"** section (one-click `POST /api/labels/{id}/cards`, no new card); truly-new words come back as a **"New words"** section (one-click `POST /api/cards` creating an audio/romanization/embedding card tagged with the label); words already under the label are skipped. Response shape: `{new:[...], existing:[...], lang}`. The older embedding-similarity deck search (`GET /api/labels/suggest-cards`) is still used by the legacy `cards.html` "✦ Suggest" button but no longer by Populate.

Per-face SRS is the central design: each card has 3 independently scheduled faces so recognition and production are practiced separately. ### Auth & sessions

Sessions are in-memory (`_sessions` dict in `main.py`): token → (user_id, expiry). Auth middleware runs on every request; unauthenticated HTML requests redirect to `/login`, API requests get 401. Sessions expire after 30 days and are purged on next login.

### Per-user day boundaries (time zones)

Everything that answers **"what day is it for this learner?"** resolves through the user's `timezone` setting (an IANA name), not UTC. This covers the 🔥 streak (`study_activity`), the daily-XP ring (`get_points_today`), daily quests (`quest_date`), and the new-cards-per-day cap (`card_faces.first_seen_date`) — they must all roll over together or the UI contradicts itself.

**Why:** UTC midnight is 5pm in California, 8pm on the US east coast, and noon in New Zealand. Two consecutive *local* study days could therefore land in the SAME UTC day, opening a phantom gap that broke a streak the learner had genuinely kept ("I studied every day and lost my streak" — the reports came from the Americas and Asia-Pacific, never Europe, whose rollover falls at ~1am local). The XP ring also reset mid-afternoon. An earlier fix made reads and writes *consistently* UTC; it did not make them local.

- **`db.py` helpers:** `resolve_timezone` (never raises — unknown/absent zone ⇒ UTC, i.e. the old behaviour), `is_valid_timezone`, `local_today_str(tz, now=None)`, `local_day_bounds(tz, day=None)` (half-open **UTC** bounds of a local day, formatted to match SQLite's `datetime('now')` so they compare directly against stored `created_at` text), plus `_tz_for(conn, uid)` / `_local_today(conn, uid)` (read on an already-open connection — a PK lookup, cheap enough to do inline on every write rather than cache-and-invalidate) and `user_today(uid)` / `get_user_timezone(uid)`.
- **Never use SQLite `date('now')` for a per-user day** — it is UTC. Pass the resolved local date as a bound parameter. The only remaining `date('now')` day comparisons are the admin dashboard's DAU/WAU/MAU and global XP-today, which are deliberately global server-side metrics rather than per-learner days.
- **Detection:** `static/app-shell.js` `syncTimezone()` reads `Intl.DateTimeFormat().resolvedOptions().timeZone` on every load and PUTs `/api/settings {timezone}` only when it differs from the stored value (so: one write on first load, then never, and again after a move or on a new device). Invalid values fall back to UTC server-side rather than 400-ing the whole settings write. Settings shows the detected zone read-only ("Day resets at").
- **Changing the zone can't cost a streak:** moving the boundary re-reads history written against the old one, which can shift the count by a day. `update_settings` reads the streak before the change and calls `db.ensure_min_streak` (insert-only) if the new reading is lower.
- **Client caches use the local day too** — `_localDateStr()` in `cards.html` / `today.html` (`xpLocalToday`, `streakCache`) and the freeze-consumed toast in `learn.html`. All of these must agree with the server's local day; a `toISOString().slice(0,10)` anywhere in this path is a bug.
- `tzdata` is in `requirements.txt` so `zoneinfo` can resolve IANA names on slim images with no system tz database.

### SRS scheduling (`srs.update`)

SM-2 with sub-day **learning steps** (`LEARNING_STEPS_MIN = [1, 10]` minutes). A new or lapsed card walks the steps before graduating to a day-level interval, so "again" reschedules in ~1 min (reappears the same session, re-queued client-side) instead of vanishing for a day. "Easy" graduates straight to 4 days; review-card hard/good/easy intervals are differentiated. Pure/stateless — pass `learning_step`/`first_seen_date`/etc. in, get the new state back.

### Study session logic (`db.get_study_session`)

Returns due review faces (next_review ≤ now) + new faces up to the daily cap (default 20 new/day, `new_cards_per_day` setting — counted against `first_seen_date = <the user's local today>`, so the cap resets at their midnight). New faces are **staggered**: a brand-new word only offers its `PRIMARY_FACE` (`target`); the other faces become eligible once the primary has graduated (`learning_step IS NULL AND first_seen_date IS NOT NULL`). **Phrase gating** (`_gate_phrases`): phrase cards (multi-word `target_text`, detected by `tokenizer.phrase_words`) are deferred until ALL constituent single-word cards have their primary face graduated — so learners always study individual words before the phrase that contains them. Over-fetches 3× and post-filters in Python. New faces ordered by priority DESC then id ASC. `db.get_due_count` applies the same staggering gate so the badge matches.

### Translation flow

`POST /api/translate` → `translation.translate()` builds a language-specific Gemini prompt → parses JSON response into up to 3 candidates (for ambiguous inputs) with target_text, romanization, notes, priority. `POST /api/cards` then generates audio via edge-tts and stores everything including the MP3 BLOB. Card romanization is always overridden by the offline oracle (`tokenizer.romanize_text`) when it produces output — this ensures tone diacritics (Thai), jyutping (Cantonese), pinyin (Mandarin), etc. are consistent with ruby annotations rather than trusting LLM-generated romanization.

### Reader generation (4 sources)

A reading can be created from: (1) a **text prompt** (`POST /api/reader/generate` → `translation.generate_reader_text`), (2) an **uploaded image** (`POST /api/reader/generate-from-image` → `generate_reader_text_from_image`, stored as a banner via `image_media_id`), (3) a **pasted URL** (`POST /api/reader/generate-from-url`), or (4) an **uploaded PDF** (`POST /api/reader/generate-from-pdf`). URL/PDF use `extract.py` (deterministic, no LLM) to pull the core text; then `main._reading_from_source` either uses the text **verbatim** when the user flags it as already in the target language (`in_target_language=true`, **no LLM call** — the AI saving) or calls `translation.translate_article_to_reading` to translate the source into the target language. **This is a LITERAL, sentence-by-sentence translation — NOT an adaptation:** `_split_source_sentences` (deterministic) splits the source into sentences kept VERBATIM; `translate_article_to_reading` translates them in batches that return a **JSON array of strings in order, one per input sentence**. Alignment is enforced by COUNT — if a batch doesn't return exactly N translations it's **split in half and retried** (down to a single sentence with a focused retry), so a flaky batch can never drop or shift the rest. It returns `segments:[{target, english}]` positionally aligned, `english` = the EXACT original sentence. **One source sentence = one unit of alignment.** `_reading_from_source` joins segments with `\n` (no sub-splitting), then re-tokenizes the content and maps each reader sentence back to its source segment by character offset. If the translated text contains internal punctuation (e.g. `。`) and gets split into multiple reader sentences, they all inherit the same source English — clicking any of them shows the correct original. The translation panel shows the exact original source, never re-translating target→English. On-demand `translate-sentence` and `tts` calls also persist back to `reader_sentences` so subsequent opens are instant. The verbatim path stores no `english` (reader translates on demand). **Self-healing alignment:** a tokenizer fix can change how a stored text splits into sentences (e.g. the pykakasi Japanese-newline bug inserted phantom `。` sentences and merged headings into the next sentence), leaving cached translations/audio at stale `sentence_idx`. `db.resync_reader_sentences(text_id, new_sents)` rewrites the stored rows to the current tokenisation — re-keys cached content by matching `sentence_text`, drops phantom/mangled rows, renumbers — and is called (only when actually stale) by both `_build_text_response` AND `reader_preload`, so EVERY downstream reader (the open response, the windowed `/preload`, page-turn preloads) sees correct indices. (Persisting matters: a stale reading is never `preload_complete`, so the frontend fires `/preload` and keys its cache by the returned `sentence_idx` — an in-memory-only re-index would be re-polluted by raw stored rows; and `upsert_reader_sentence` can't fix it because it `COALESCE`s and never updates `sentence_text`.) Old readings heal on next open; dropped translations re-fetch on demand. All four converge on `db.create_reader_text` + `_build_text_response`; per-sentence translation/audio is generated on demand / via the preload route as usual. CEFR `difficulty` shares `translation._DIFFICULTY_INSTRUCTIONS`.

**Reader home (redesigned):** `My Stories`/`Community` is a segmented pill control; the generate form is collapsed behind a brand-colored **"New reading"** card (`#new-reading-card` → `toggleGenForm()`, auto-opened when the library is empty); saved stories render as cards with a gradient cover tile (first title character, gradient by `id % 4`), language/CEFR/date chips (`list_reader_texts` now returns `difficulty`), and the existing share-visibility dropdown + delete. **Generate form has 3 modes** (`static/reader.html`, `setGenMode`): **✨ AI Story** (prompt and/or image — the only mode with length controls), **🔗 From URL**, and **📄 From PDF**. All three have a **Level/Difficulty** selector. URL/PDF default to **"Keep original"** (no simplification — verbatim or literal translation, current behavior). Selecting a CEFR level (A1–C2) adapts the text: for translated imports, `translate_article_to_reading` receives `difficulty` and adds CEFR instructions to the translation prompt; for "already in my target language" imports, `translation.simplify_article` rewrites each sentence at the chosen level (same sentence-by-sentence alignment contract, `{target, english}` where `english` = original). "Keep original" + "in target language" = fully verbatim (no LLM call).

**Lazy/windowed preload (so long imports don't fire N LLM/TTS calls on open):** `POST /api/reader/texts/{id}/preload` takes optional `start`/`count` query params — with `count` set it processes only that sentence window (skipping already-cached), returning all cached sentences + `total_sentences` + `preload_complete` (whole-text). The frontend (`static/reader.html`) preloads only a render-ahead window (`PRELOAD_SENT_WINDOW` = 10 sentences, covers the current page + 1 ahead) on open and again on each page turn (`preloadAround(pageIdx)`, deduped by window-start in `_preloadPromises`); everything else stays on-demand — tapping a sentence/word does a single live `translate-sentence`/`translate-word` call (persisted back to `reader_sentences` so it's cached for future opens), and audio mode falls back to per-sentence `/tts` (also persisted). So a 60-sentence article costs ~10 sentence-translations on open instead of 60. `count` omitted = legacy full preload (used when a story is already fully cached). Community stories aren't owned (can't call `/preload`), so `preloadAround` is gated by `_canPreload` (snapshotted at `showReaderView` entry, before it resets `_isCommunityStory`).

**Dynamic pagination:** pages are sized to fit the viewport rather than using a fixed sentence count. `computePageBreaks()` renders all sentences into the container (hidden), measures their heights against the available viewport space (below the header/panel, above the nav bar), and builds `pageBreaks[]` — an array of sentence-start indices. Pages recompute on window resize (debounced 200ms) so orientation changes and desktop resizing adapt instantly. Helper functions `_totalPages()`, `_pageStart(p)`, `_pageEnd(p)`, `_pageForSentence(si)` replace all the old fixed-count arithmetic. Minimum 1 sentence per page.

**Sentence boundaries — ONE source of truth (alignment invariant):** the translation/audio cache is keyed by the server's `sentence_idx`, and the reader renders + looks up sentences by index, so the client and server MUST agree on sentence boundaries exactly (count + order). They used to each split independently — the server in Python (`tokenizer.split_sentences`) and the client in JS (`buildSentences`) — and **drifted three different ways**: the client kept empty `\n` paragraph-break "sentences" the server dropped (off-by-N on every multi-paragraph story — a Japanese story showed sentence 9's text with sentence 13's English); the client's ender regex omitted the Arabic full stop `۔`/question mark `؟` the server splits on (off-by-N for `ar`/`ur`/`fa`); and the two tracked different quote characters (the server even tracked straight `"`, the same code point for open+close, so its depth only ever incremented and splitting stalled inside the first quote). **Fix:** `tokenizer.split_token_sentences()` is now the single splitter — it returns token *groups*; `split_sentences()` is a thin string wrapper over it; and `_build_text_response`/`reader_community_text` ALWAYS send those groups as `sentence_groups`, which the reader renders directly instead of re-splitting. The client `buildSentences()` remains only as a defensive fallback (it mirrors the server: trims edge-whitespace tokens, drops empty groups). Quote tracking uses directional pairs only (`“«「『` / `”»」』`); straight quotes are untracked. **Any change to sentence splitting goes in `split_token_sentences` alone.**

### AI Learning Path — just-in-time planner + broad lessons

Language-agnostic — works for every `LANG_INFO` language (native script + per-language romanization via `tokenizer`; the `grammar.py` conjugation oracle only engages for French). Two adaptive LLM calls **per lesson**, all in `learning.py`, orchestrated by `main._author_next_lesson` (the per-lesson helper) which `main.next_lesson` loops `count` times (1–6, so the learner can browse ahead). Each looped call re-reads live state, so each lesson adapts to the ones just authored **and** to what the learner did elsewhere (tutor chat, new flashcards):

1. **Planner** (`plan_next_lesson`) — once per lesson. One cheap LLM call picks the SINGLE best next lesson from live learner state (concept registry, the in-progress chapter, weak skills/`mastery`, `get_known_words` + a CEFR spread, `get_weak_cards`, **`get_recent_cards`** = words just added via tutor/flashcards, `learner_profile`). Returns a `lesson_spec`: `{chapter_action: continue|new, chapter, skill, scope: broad|narrow, focus: new|exceptions|review, target_items[], rationale}`. Two learner-facing dials feed the pipeline (Phase 3): the **`course_focus`** setting (balanced/grammar/vocab/conversation → one steering line in the planner prompt, `learning.COURSE_FOCUSES`; set at course creation via focus chips or in Settings) and the **`lesson_length`** setting (quick/standard/thorough; set in Settings or via the lesson intro sheet's length chips). Both validated in `main` (`_valid_course_focus`/`_valid_lesson_length`, unknown → default). **Length no longer shapes generation** — every lesson is authored ONCE at maximum depth (`_AUTHOR_DRILLS`=10–14, 12–16 with review; `_AUTHOR_STEPS`=3–4; thorough teach) and the author TAGS each drill with a `tier` (core/standard/extra, `learning._norm_tier`, defaulting missing→standard). The lesson PLAYER then serves a subset by tier (`_trimForLength` in `learn.html`): quick=core, standard=core+standard, thorough=everything. This makes "thorough" honest (all the content really was authored) and lets a length change reshape ANY stored lesson instead of only shrinking a freshly-generated one — you can't add drills that were never generated. Pre-tier lessons (no `tier` on any exercise) fall back to a proportional `_LEN_FACTOR` trim, so they behave exactly as before. `learning.LESSON_LENGTHS` is now just the tuple of valid `lesson_length` values. **Coherence** lives in the chapter it carries forward; **adaptivity** lives in re-deciding every lesson. A lesson is a *satisfying chunk*: a whole grammar family in one go (e.g. all regular -er verbs + their forms in `target_items`), with irregular/spelling-change cases scheduled as their own later `focus:"exceptions"` lesson; or a themed set of 4–8 vocab words.
2. **Author** (`author_lesson`) — once per lesson. One LLM call authors the WHOLE lesson (teach blocks AND drills) for the skill + items handed to it (`main._concepts_from_spec` maps the spec → concepts: a grammar skill is ONE concept carrying its forms as `items`; a vocab lesson registers EACH `target_item` as its own concept). The planner's `scope`/`focus`/title ride in as a `brief`. Grammar and vocab are **not** segregated — the model sees one palette and picks what the point needs. This unified authoring is what makes teach and practice cohere.

**Bite-sized steps (lesson redesign Phase 1, `docs/LESSON_REDESIGN.md`):** the author returns `steps: [{title, teach:[blocks], drills:[...]}]` (2–4 per lesson) instead of one flat teach+drills pair — step 1 is a **warm-up** (the interleaved review drills go at its front, then the gentlest new drill), middle steps teach ≤2 blocks then immediately drill them, the final step is mixed drills with no new teaching. `assemble_lesson` maps each authored step → one player segment (drill dedup spans steps; the legacy flat shape still wraps as a single step, so old model replies/old lessons keep working) and emits the construction drill as its **own final "AI Speak" segment** (`{title:"AI Speak", speak:true, teach:null}`, one `construction_drill` per grammar concept) instead of trailing the drill run — 3 turns (`tutor.LESSON_DRILL_TURNS`), skippable in the player via a ghost button that counts as a formative pass. A new teach block type **`quick_check`** (`{question, options 2–3, answer, why}`) puts a one-tap formative check inside the teach flow: validated + shuffled server-side in `grammar_lessons._clean_block` (answer placed by us, index correct by construction), rendered by the player as an ungraded mini-drill (a correct tap bumps combo/XP; a miss never breaks the combo and joins no mistake queue / mastery ledger). **Player chrome** (`static/learn.html`): a **segmented step bar** (one `.step-seg` pill per segment, grammar-tinted for the speak segment) replaces the single progress bar on both the teach and exercise screens, with a "Step i of n · title" `.step-tag`; the teach screen is a **tap-through card pager** (one block per screen, dot progress, intro on the first card, Continue advances) — gated off for foundations and legacy `teach.items` lessons, which keep the single scroll page.

**Chapters** are emergent, not pre-planned — but **bounded**: the planner controls them lesson-by-lesson via `courses.active_plan` (`{title,objective,summary,budget}`); opening a new chapter (`chapter_action:"new"`) closes the previous one into a unit (`db.close_unit`), which keeps the `learn.html` roadmap working unchanged. Three deterministic guards stop the old "In progress for dozens of lessons" failure: (1) **budget** — the planner picks `planned_lessons` (2–6) at chapter open; once the open-lesson count (`ctx["open_lessons"]`, derived not stored) reaches it, `_author_next_lesson` forces `chapter_action:"new"` regardless of what the model answered (the prompt also says it MUST); (2) **running summary** — each authored lesson's summary is rolled into the chapter summary, so "continue until the objective is met" is decidable from the prompt (a frozen summary made every chapter look unfinished forever); (3) **completion-time close** — `main._maybe_close_chapter` (called from the `/complete` route) seals a fully-generated, fully-completed chapter into a unit immediately, so the checkpoint node appears without waiting for the next generation. The in-progress banner shows the chapter title + "Lesson i of ~budget" (`get_course.active_chapter`). The planner prompt also now receives **completed-unit summaries** (`_units_block` — previously fetched but never wired in) and, on a re-plan, an `avoid_feedback` block.

**Textbook units (PDF → reviewed source → multi-lesson unit):** managed from the dedicated **`/textbooks`** page (see Page routing) — upload, read by chapter, then turn a chapter into a unit. Upload (`POST /api/courses/{id}/textbooks`) asks for an editable name, extracts text per visible PDF CropBox (`extract._extract_visible_page_text` prevents split-spread PDFs from leaking the neighboring page), cleans it per page, extracts useful embedded raster visuals, and persists the parsed book immediately. Cleaning (`textbook.clean_pages` → `strip_repeated_lines`) drops running headers/footers/watermarks by counting lines whose **digit-masked** form recurs on ≥30% of pages — which means a book whose pages differ only by a number (numbered drills, a repeated table scaffold) can have EVERY line look like a header. A page holding ≥`_MIN_PAGE_CHARS_TO_PROTECT` (120) chars is therefore never stripped to nothing: it's kept whole minus bare page numbers, since losing a page of source silently starves chapter detection and lesson authoring, while a genuinely header-only spacer page has too little text to qualify and still cleans out. A separate retryable `POST /api/textbooks/{id}/analyze` fast-model call proposes editable textbook-unit ranges, so transient AI failure cannot discard the uploaded book. `plan_source_unit` inventories every teachable source concept, requires each inventory ID to map to exactly one of 1–12 lessons, and verifies every lesson's purported verbatim excerpts occur in the approved text; malformed or incomplete coverage is rejected — but **retried once first** (`textbook.PLAN_ATTEMPTS`, mirroring `DETECT_ATTEMPTS`; the plan returns `llm_calls` so metering follows what was actually spent), because a rejected plan is usually model wobble on an unchanged prompt and the learner's only recourse was tapping Create again and sitting through the whole flow. Lesson **authoring** retries the same way (`main._AUTHOR_ATTEMPTS` in `_author_and_persist`, covering both a failed call and a reply whose drills all fail validation, leaving no exercises); a failed attempt never pops the queue row, so Generate can always try again. `POST /api/textbooks/{id}/unit` **creates a `theme='textbook'` `course_units` row up front** (`db.create_textbook_unit_row`, tagged with `textbook_id`/`chapter_idx`), scopes the whole queued plan to it (`lesson_queue.unit_id`), and authors lesson one immediately via `_author_textbook_lesson`; the rest are authored from the unit's buttons on Learn (`POST /api/course-units/{id}/next-lesson`) or ahead of the learner in the background — **never** through the AI course's `_author_next_lesson` (which no longer touches the queue), so textbook and AI lessons don't interleave. **One unit per chapter:** the route 409s (with the existing `unit_id` + lesson counts in `detail`) when that chapter already has a unit, unless the caller sends `replace: true` — the reader then offers "Regenerate lessons", which deletes the old unit only AFTER the new plan is in hand, so a failed re-plan leaves the existing lessons untouched. Individual lessons and whole units are deletable (`DELETE /api/lessons/{id}`, `DELETE /api/course-units/{id}`). Completing a textbook unit still informs the AI planner: its lessons are ordinary `course_lessons`, so `course_concepts` (author time), `concept_mastery` + `_auto_add_lesson_vocab` (completion) all fire as usual. The author is explicitly allowed to reuse clear textbook wording/examples verbatim and must not replace them with generic same-topic content. Pure vector drawings remain a known limitation.

**Mid-page unit boundaries (splitting a page between two units):** boundaries are page integers, but a unit can begin/end partway down a shared page, so each chapter may carry optional `start_anchor`/`end_anchor` — one verbatim line marking where its content begins on its first page / where the *next* unit begins on its last page (JSON fields in `chapters_json`, no migration). `textbook.split_page`/`unit_pages`/`format_unit_source` trim the first page before `start_anchor` and the last page from `end_anchor` onward (line-based, whitespace-tolerant; a no-longer-matching anchor safely keeps the whole page). **`_anchor_line_index` matching order matters**: an EXACT normalized line wins first, then a rejoined run of consecutive lines (`_MAX_SPAN_LINES`=12 — a PDF that positions each word separately extracts one word per line, and the AI's anchor is verified against the page as a whole by `_source_contains_quote`, so it can legitimately name a "line" the page never stores as one), then a prefix match of at least `_MIN_PREFIX_MATCH`=8 chars. Taking the first loose prefix instead let a short earlier line ("Unit") hijack the boundary and trim a unit down to nothing; requiring exact-only made a wrapped anchor unfindable so the split verified and then silently did nothing. `extract._line_matches` and `textbooks.html`'s `_tbAnchorIdx` mirror this order — change all three together. `_norm_chapters` preserves + cleans the anchors and lets two adjacent units **share exactly the boundary page** (`next.start == prev.end`) when either side is anchored — an unanchored overlap is still resolved forward. **Generation respects splits from any entry point:** `create_textbook_unit`/`create_textbook_lesson` read anchors from the request payload, **falling back to the matching chapter's stored anchors** (`_chapter_anchors`) when the payload omits them, then build the source via `format_unit_source` (used whenever the caller doesn't send an edited `source_text`). So a split set in the divisions editor applies even though the dedicated page's "Turn into lessons" sends only `{start,end}`. **UI (single home — the dedicated `/textbooks` page):** the chapter divisions editor (`textbooks.html`) shows a **Split page** control on any chapter that shares/touches a boundary page with its neighbour — it renders that page line-by-line, and tapping a line sets BOTH neighbours' anchors + makes them share the page (greying/striking each side's portion), persisted through the same `PUT /chapters` (which now round-trips anchors); a **✂︎ split** tag marks split chapters in the read-only TOC, which also spells out each cut ("ends on p12 before “Lesson 4”"). **Validating a split in the reader:** `GET /api/textbooks/{id}/splits` returns **every** unit boundary as `{page, line, above, below, y, kind, edge, boundary}` — `kind:"mid"` for an anchored mid-page cut and `kind:"page"` for a boundary that falls on a clean page break, emitted TWICE (bottom of the earlier unit's last page, top of the next unit's first page) so every division in the book is visible where it happens; only anchored marks pay for the page-text lookup. `boundary` is the chapter index i the mark divides (i / i+1). Every marker's ✂︎ chip is tappable → `openBoundaryMenu` → **"Move the split"** (enters the drag editor) or **"Merge into one unit"** (`POST /api/textbooks/{id}/chapters/merge {index}` → `textbook.merge_chapters` + `db.collapse_unit_chapter_idx`), which is what lets unit structure be corrected entirely from the page instead of the text-based divisions editor. **Mid-page and page-edge boundaries are the same draggable object**: in split-edit mode the boundary the current page touches (`_seEditBoundary` → mid-page shared, or the clean break at the page's top/bottom) is one rule, and `_seSnap`/`_seApplyTarget` slide it freely between candidates — a text line (mid-page cut, anchored) or the top/bottom edge (clean page break). Dragging a green edge marker onto the page body makes it a mid-page split; dragging a mid-page rule off the top/bottom turns it back into a clean break that then renders on the neighbouring page too (both-sided `kind:"page"` marks). The ✕ on the rule only undoes a split created in the same session; an existing boundary reverts to a clean break by dragging to the edge, and merges via the menu. A merge **renames the survivor with one cheap LLM call** (`textbook.name_merged_unit` over the combined pages — each old title only described half of the merged unit); a model failure or exhausted quota falls back to joining the two titles, because a merge must never fail over its name. `y` comes from `extract.locate_page_lines`, which re-extracts that page with pypdf's positioning visitor, rebuilds its lines, and reports the anchor's height as a 0–1 fraction of the crop box (placed in the whitespace ABOVE the matched line, since the visitor reports baselines — `extract._RULE_GAP_FRACTION`=0.68 of the way up toward the previous baseline, NOT the midpoint, which lands on the cap height and clips the glyphs). The reader fetches it after opening (never blocking the first page) and draws a dashed rule across the page image at that fraction plus a small ✂︎ chip in the margin; the same boundary is marked in the extracted-text pane (lines above dimmed, a labelled dashed divider, the anchor line highlighted) — that copy is what generation actually trims, so the two views cross-check each other. `y` is null when the anchor can't be located (a vision-transcribed page, a hand-edited anchor), and the text-view marker still shows. The chapter caption names BOTH units on a shared page. The JS mirrors the Python trimmer so preview == generation. Editing a chapter's page range clears its anchors. **Placing a split by dragging (the reader's ✂︎ button):** `GET /api/textbooks/{id}/page/{n}/lines` (`extract.page_line_positions`, sharing `_page_rule_positions` with `locate_page_lines` so a dragged position is exactly where the rule lands) returns every line on the page with its rule height, cleaned through `textbook.clean_page_text` so the anchor produced matches the stored copy the trimmer reads. Split mode (`toggleSplitEdit` in `textbooks.html`) overlays the rendered page: tapping inserts a split at the nearest line, the rule is draggable and **snaps to a real line** (a split is a verbatim line, never a coordinate), ✕ removes it, and the extracted-text pane mirrors the DRAFT boundary throughout (`_splitsOn` returns the draft while editing) so both views cross-check before saving. Inserting on a page interior to a unit **splits that unit in two** and asks for the new unit's name (defaulting to the anchor line, which is usually the heading, and following the drag until edited); removing a split made in the same session merges the unit back, while removing a pre-existing one keeps both units and just reverts to a clean page break. The draft is book-wide, so page turns keep editing and one Save (`PUT /chapters`) persists every change. Overlay chrome lives in the **right margin** — a rule sits between two lines, so anything anchored left covers the words being validated. Books with no page image (text-only) say so and point at Chapters → Edit divisions, which remains the keyboard/line-list path. (The old learn.html review-sheet split editor was removed — splitting lives only on the dedicated page.) **AI second pass (`textbook.refine_chapter_boundaries`):** the page-range detector only emits whole-page ranges, so it can't propose mid-page splits. After `detect_chapters`, `/api/textbooks/{id}/analyze` runs one cheap LLM call per consecutive gap-free boundary (bounded by `MAX_REFINE_BOUNDARIES`=12) that shows the model the text on **both sides** of the divide (`_REFINE_WINDOW_LINES`=45 lines each) and asks for the exact verbatim line where the next unit begins + which page it's on; a server-verified line on a shared page becomes an anchored mid-page split (else a clean page break is left alone). The boundary calls run **concurrently** (`REFINE_CONCURRENCY`=4) under a wall-clock `REFINE_BUDGET_S`=45 s budget — serially they stacked minutes of latency onto detection and timed the whole request out, which is what made AI splitting look flaky. Separately quota-gated + best-effort — if the learner can't afford the extra calls, a boundary errors, or the budget runs out, the page-range chapters stand. **`/analyze` persists pass 1 before pass 2 runs** (and returns `refined`), so a slow/failed refinement never discards good detection; `detect_chapters` returns `(chapters, llm_calls)` and retries once on an unparseable/empty reply (`DETECT_ATTEMPTS`), with metering charged per actual call.

**Chapter → vocab flashcard deck (quick path, no lesson authoring):** a lighter sibling for when the learner just wants the WORDS. The SAME source-review screen has a **📇 Build vocab deck** button (`buildVocabDeck` in `learn.html`) beside “Create multi-lesson unit”. `POST /api/textbooks/{id}/vocab` → `textbook.extract_chapter_vocab` runs ONE cheap reader-model call per ~9k-char chunk over the approved page range/edited text (no grammar teaching, no drill authoring), preferring the book's own vocab lists, deduping by native target, capped at `textbook.MAX_VOCAB_ITEMS`=80. It returns a flat `{target, gloss, example, cefr}` list; the route adds offline-oracle romanization (`tokenizer.romanize_text`, never the model) and `in_deck` flags (`db.get_word_statuses`). The learner reviews an editable checklist (`renderVocabReview`: new/already-in-deck/found stats, per-row CEFR pill + jyutping ruby, dimmed in-deck rows, select-all-new/clear, deck-name field, optional “save as shareable deck”), then commits via `POST /api/vocab-deck` (`create_vocab_deck`): creates a `📕 {deck}` label, bulk-creates cards (audio is left NULL and generated lazily on first `/api/audio` play, like deck imports; background embeddings; CEFR persisted), skips words already in the deck, and optionally snapshots a `shared_deck`. The success screen’s **Study N words** deep-links `/cards?label_id=…&study=1`, so studying reuses the existing label-filtered SRS with zero new study code. Both routes meter per LLM chunk via `_textbook_metering`.

**AI vision re-extraction (`extract.render_pdf_pages` + `textbook.transcribe_pages`):** deterministic `pypdf` text mangles the books this pipeline most wants — **2-up spreads** interleave two logical pages, **interlinear** layouts scramble the romanization↔gloss alignment, **romanization-only phrasebooks** carry no native script at all, and **scanned** pages have no text layer. So the upload keeps the source PDF (`pdf_media_id`) and `POST /api/textbooks/{id}/transcribe {start,end}` renders that page range to images and has the vision model (`access.model_reader`, one metered call per page, bounded to `textbook.MAX_VISION_PAGES`=20) transcribe each into clean, linear, **native-script** text — reconstructing the native script from romanization when the page lacks it, honoring reading order, and dropping page furniture — then overwrites those pages via `db.update_textbook_pages`. It's **user-invocable** from the source-review screen (the “✨ Re-read these pages with AI” button, `reReadSource` in `learn.html`) regardless of the heuristic, because the highest-value cases (missing native script, scrambled 2-up order) don't look like byte-level garble. The upload response's `low_text_quality`/`low_text_quality_reason` (from `extract.assess_page_quality`, language-aware) only *nudges* the learner toward it. Best-effort per page (a page that fails to transcribe keeps its original text); the transcript goes through the same `clean_page_text` normalization as pypdf text.

**Gamification (`static/learn.html`, Phase 5):** the lesson player has Duolingo-style juice. (1) **Combo meter** — `player.combo` counts consecutive first-pass correct answers (reset on a first-pass miss); an amber "🔥 ×N" chip in the player bar pulses on each increment (shown at N≥2), and a "+N XP" floats up. XP per correct = `comboXp` (base 10 + escalating combo bonus, capped). (2) **XP results tally** — the results screen animates an XP count-up with a `★ Perfect lesson` bonus (+25, all first-pass correct) and a `🔥 Best combo ×N` badge; a perfect run fires a double confetti burst. Deterministic recombination, no LLM. **The recogniser is bounded, because `speechSupported()` only proves the API exists.** `start()` can return into total silence — no `onstart`, no `onresult`, no `onerror`, no `onend` — on an Android build with no recognition service behind it, on iOS when something else already holds the microphone, or when the speech backend is unreachable; nothing further ever fires, so the drill sat on "Listening…" with Check disabled and no event left that could release it (the reported "voice input freezes the app"). So every listen is bounded twice — `SPEECH_START_MS`=3 s (the recogniser must say it started) and `SPEECH_MAX_MS`=20 s (it must finish) — a timeout ends as `uncheckable` rather than wrong, a device that fails either is written off for the session (**`_speechDead`**, checked by `_canSpeakVariant` so later steps stop offering drills that can only time out), and a retry clears the previous attempt's `blocked` verdict so being heard on the second try still counts. Handlers are guarded by instance identity and `stop()` **aborts** rather than merely stopping: `stop()` alone keeps the microphone (and on iOS a recording audio session, which silences our own playback) after the learner has left the drill, and a superseded recogniser's late events must not write to the UI. Grading is bounded too — `_timedFetch` caps `/api/lesson/check` (`GRADE_TIMEOUT_MS`) and `/api/ruby` (`RUBY_TIMEOUT_MS`), since a hung request holds `onAction`'s `_grading` flag and the disabled footer button for the rest of the session; a failed ruby lookup is evicted from `_tokenCache` instead of being cached as a permanent failure; the homophone romanizations are fetched **in parallel** behind a "Checking…" line (four sequential round trips before the judge call, with nothing on screen, is indistinguishable from a hang). And a `grade()` that THROWS is caught in `onAction` (`player._gradeFailed`) and routed into the same grader-unreachable path — the exception used to escape with the button still disabled and no verdict rendered, which ended the lesson. **Live feedback is part of the drill, not decoration**: a mic button that says "Listening…" and then nothing for two seconds is indistinguishable from a broken microphone, so the drill renders the recogniser's OWN progress events — `onaudiostart`/`onsoundstart`/`onspeechstart`/`onspeechend` → "Microphone open" → "Picking up sound…" → "Hearing you…" (the state that proves the mic works, so it is the one styled to be noticed) → "Working out what you said…" → "Got it — tap Check" — and shows **interim** transcripts as they stream, muted with a caret (`.sp-live`), so watching the words appear IS the feedback. An interim guess is never dressed as the verdict (`showHeard(text, live)`; only a final result gets "I heard:"). A **🔎 Details** toggle (`localStorage.speechDebug`, off by default, persisted) opens a plain-text diagnostics panel: the setup (BCP-47 tag vs drill lang, expected answer + accept-set, the two timeouts) then a millisecond-stamped trace of every recogniser event, every alternative with its confidence, and the grading path — `gradeSpoken` and `gradeFreeText` take an optional `log` callback and report which comparison decided it (sounds-like match / romanization pair / server judge / not counted). Speech recognition fails differently on every device and "it didn't work" is not a reportable bug; this is what makes it one. `tests/test_speaking_drills.py` drives the shipped renderer under node for all of it. **SRS deck integration (both directions):** `db.get_known_words` (graduated target faces with traction, strongest first, cap 150), `db.get_weak_cards` (low-ease / relapsed), and `db.get_recent_cards` (newest-added, the cross-app signal) are fetched per lesson. **Redundancy control — what the planner can SEE, then three dedup layers.** Redundancy was mostly a *visibility* problem, not a filtering one, so `db.get_next_lesson_context` returns two things beyond the concept registry:

- **`taught_words`** — every native word the course's lessons actually taught, derived from each lesson's stored `concepts_json` (`db._lesson_words`: a vocab concept contributes itself, a **grammar concept contributes its `items`**), first-lesson-wins. This is the blind spot it exists for: `create_lesson` registers only the top-level concept in `course_concepts`, so a grammar lesson's words — most of the vocabulary in a grammar-forward course, and most of a textbook unit's — were invisible to both the planner prompt AND `_filter_new_concepts`, which is how a later lesson re-taught them under a fresh key. NOT completed-only (unlike `get_course_vocab`): the planner must not re-teach what it has already GENERATED.
- **`lesson_index`** — every lesson in the course (`{lesson_num, title, summary, source}`, `source` = `ai`|`textbook`), so the planner isn't judging repetition from three recent summaries alone. Rendered by `learning._lesson_index_block` (cap `_LESSON_INDEX_CAP`=40, textbook lessons marked 📕); `_taught_words_block` renders the words (cap `_TAUGHT_WORDS_CAP`=140). Both sections are omitted when empty so the first prompt of a course stays small.

Then the filters, in order:

1. **String** (`main._filter_new_concepts`) — drops concepts already registered (by key, or by native label for vocab), any vocab whose label is in **`taught_words`** or in the learner's deck (`known_texts`), and dupes within the plan itself; `INSERT OR IGNORE` on `course_concepts` would otherwise swallow duplicates silently.
2. **Semantic, concept level** (`main._semantic_dedup_grammar`) — embeds GRAMMAR concepts' label+gloss (shared `embedding_cache`, sentinel lang `__concept__`, key `f"{lang}|{text}"`) and drops any at cosine ≥ `_CONCEPT_DUP_THRESHOLD`=0.86 vs already-taught grammar, catching paraphrased keys (`present_er` vs `er_verbs_present`). Vocab is exempt (near-synonyms are legitimately distinct words).
3. **Semantic, lesson level** (`main._semantic_dup_lesson`) — the one that catches the failure learners actually report: two lessons teaching the same thing under different names, with different or no overlapping words ("Ordering at a restaurant" → "At the café"). The planned lesson's **topic** (`_spec_topic_text`: the skill gloss + its items' English glosses) is embedded against every existing lesson's `title — summary` (sentinel `__lesson__`, cosine ≥ `_LESSON_DUP_THRESHOLD`=0.87, `_LESSON_DEDUP_CAP`=60 most recent). Neither concept keys nor words are involved, so it sees repetition the other two structurally cannot.

Both semantic passes share `main._embed_texts` (cache-through embedding) and are **best-effort** — any embedding failure degrades to the string filter. `main._plan_rejection` turns either failure into the `avoid_feedback` text; a rejected plan is **never shipped**, the planner re-runs ONCE with the clash named (the concept keys, or the specific lesson it repeats), and the request 502s if that still fails. The re-plan only has to clear the concept guards — re-running the topical check could reject forever on a course whose remaining ground genuinely neighbours what's taught. **Queued textbook lessons are the exception**, and it is asymmetric on purpose: `_author_textbook_lesson` runs the string filter (so a book lesson doesn't re-register words an earlier lesson already taught) but **never** the two semantic passes and never `_plan_rejection`, and falls back to `deduped or raw_concepts` — if the filter empties the plan, the book is taught anyway, because explicit user material outranks "already known". So the guarded direction is textbook-first → AI-later; an AI lesson can't re-teach what the book covered, while the book is always allowed to cover its own ground. `_registry_block` caps prompt registries at the 150 most recent concepts.

**Debugging redundancy on a real course:** `scripts/lesson_overlap.py` (read-only, no LLM) compares the *stored* lessons pairwise on four signals — taught words, drill answers, concept keys, title tokens — and annotates each flagged pair with WHICH guard let it through, plus a count of words invisible to the planner. `docker compose exec -T app python scripts/lesson_overlap.py --list` then `--course N --verbose` (or `--json`).

Principle **liberal in what you SHOW, strict in what you GRADE**:

- **Teach blocks** are authored freely as an ordered list of typed blocks (`prose`, `table`, `examples`, `contrast`, `note`) — a page of a textbook. Rendered client-side by `renderBlock` (learn.html); romanization on every cell is recomputed by us. **No hardcoded language-specific presentation, no raw HTML.**
- **Drills** are authored as `{correct answer + distractors}` (a few constrained kinds: recognition / production / listening / cloze / reorder / match) — **never an answer index**. We assemble the graded exercise ourselves (`assemble_lesson` → `_assemble_drill`): place the known-correct option, shuffle, index. So the answer key is **correct by construction**. Free non-LLM oracles still guard graded items: **romanization** via `tokenizer.romanize_text` (never the model), and **French present-tense** cloze answers/options via `grammar.py` (`_conj_cloze`, fires only when the model tags `verb`/`person` and its answer is a real paradigm cell; else `_free_cloze`). Drills that can't be validated are **dropped**.
- **Drill feedback explains in ENGLISH, always.** Both judge prompts (`build_typed_answer_judge_prompt`, `build_lesson_drill_judge_prompt`) require the `note` in English while `corrected`/`alt` stay in the target language — they are answers, not explanations. Told to act as a Cantonese tutor a model will happily explain the mistake in Cantonese, which is unreadable to exactly the beginner who just made it. A prompt is a request, not a guarantee, so `tutor._english_note` is the deterministic backstop: it drops a note that is mostly non-Latin letters (English quoting native words is kept). Script can't tell French from English, so a Latin-script target still relies on the prompt. Same principle as the card-ask pop-over, which never replies in the target language.
- **Typed free production (`translate` / `type_cloze` → exercise type `type_answer`)** is the one gradeable kind with no options, so "correct by construction" cannot apply — a lesson of pure multiple choice lets a learner finish without ever writing the language, which is what these exist to fix. The author supplies `answer` plus an `accept` list of other valid forms (deduped against the answer at assembly), and the **author prompt requires a minimum mix** — ≥3 `translate`, ≥2 `reorder`, ≥1 `type_cloze` — so the requirement lives in generation, not in a client-side filter. Grading is two-stage in `POST /api/lesson/check`: `tutor.answer_matches` (offline accept-set compare — free, instant, works with no key) and only on a miss `tutor.judge_typed_answer`, one liberal LLM call that grades from the MEANING and accepts any natural rendering. **An accepted variant shows BOTH answers** — when the judge accepts a different-but-valid rendering (`exact:false`), the player prints the lesson's own answer beside the verdict (`_expectedLine` + the controller's `expectedText()`; suppressed when the "Better:" line already is that answer), and `build_typed_answer_judge_prompt` requires the `note` to name how the two DIFFER against that specific expected answer rather than just approving. "Correct — that works too!" alone left the learner with praise and no idea what the other way of saying it even was. **Three outcomes, not two** — an unreachable grader (no key, quota, network) returns `checked:false`, and the player then leaves score/combo/mistakes/mastery untouched and just reveals the answer, because the learner was quite possibly right. Never let a missing key 503 this route: mid-lesson that reads as the lesson breaking. The client mirrors the normalisation in `_typedMatches`/`_normTyped` so an exact answer costs no round trip and still grades offline — **keep it in step with `tutor._norm_for_compare`**, which casefolds and then drops EVERY punctuation mark, symbol and space: a translation drill isn't testing punctuation or spacing, so a right answer with a comma in it (or spaced-out CJK) must not be sent to a paid grader to be told it was right. `answer` is the **canonical** form — the one the learner is shown whenever they produced anything else — and `accept` lists the OTHER equally natural renderings. The author prompt asks for them but explicitly does **not demand** them: many sentences have exactly one natural rendering, and an invented alternative marks a wrong answer correct, which is worse than the moment a judge takes. `tutor.match_kind` / the client's `_matchKind` separate an `exact` hit from an `accept` one, so an alternative reads "Correct — that works too!" **with the canonical answer beside it**, for free. Typed drills rank hardest in `_testOutRank` and `_checkpoint_difficulty`, and are deliberately excluded from the lightning round (typing against a 60-second timer). `onAction` is `async` because of this — `controller.grade()` may return a promise, and `player._grading` guards the double-tap.
- **The lesson progress bar is ONE continuous track, not per-step pills** (`updateBar` / `_segWeight` / `_teachCards` in `learn.js`). Fill = (work done / total work) across the whole lesson, where a step's work is its teach cards plus the drills *this run* will actually play; thin `.step-tick` marks sit where each step ends, and the "Step i of n · title" caption carries the rest. Separate pills could not be both even and honest — sized equally they advance at wildly different rates (8 drills crawl, 2 leap), and sized by content the one-drill AI Speak step renders as an unreadable sliver next to an eight-drill step. Teach cards count as progress (paging through them used to move nothing), a step left empty by `_trimForLength` is dropped rather than reserving a slice nothing can fill, and "Step i of n" counts only visible steps. The fill is monotonic by construction. `tests/test_lesson_progress_bar.py` runs the real functions out of `learn.js` under node with a stub DOM (including a monotonicity walk).
- **Distractor hygiene** (all deterministic, all free — string work plus the offline romanization oracle). The shared guards live in `grammar_lessons.py` (the lower module, so `learning.py` can import them without a cycle) and apply to EVERY graded choice item — drills, cloze, and teach-flow `quick_check`s alike, since a leaky quick_check is as useless as a leaky drill:
  - `_pick_options` drops distractors equal to the answer after `_norm` (casefold, whitespace, terminal punctuation, leading the/a/an/to) so no drill has two arguably-correct options.
  - **`drop_cross_script`** — every option must be in the SAME script as the answer. The model periodically mixes languages inside one option list (an English gloss among native-script foils, or the reverse); the odd one out is then visibly the answer and the learner picks it **without reading**. Backed by **`tokenizer.script_class`** (`"native"` if the string holds any non-Latin letter, `"latin"` if Latin-only, `""` if it has no letters and so can't be judged) — deliberately **language-agnostic**, so it covers every non-Latin target at once and is a correct no-op for Latin-script targets, where English and French are both `latin` and no foil is distinguishable this way. Generalizes the old CJK-only listening filter; applied to recognition, production and listening.
  - **`drop_homophones`** — drops distractors that romanize identically to the answer. Undecidable whenever the question is "what did you hear" (listening) or "how do you say this" (production, cloze, most quick_checks): 唔該借**支**筆 and 唔該借**枝**筆 are both `m4 goi1 ze3 zi1 bat1`, both correct classifiers for a pen, and the learner has nothing to choose on. Romanization is the offline oracle, never the model, and is empty for Latin-script languages — so this is a no-op there, which is right: French *parle/parles/parlent* are homophones but are distinguished **in writing**, which is exactly what a written cloze tests. (Note 個/嗰 — cited as a homophone pair in an older comment here — are `go3`/`go2`, a real tone contrast and a perfectly good listening drill.)
  - **`drill_is_sane` / `block_is_sane` (`learning.py`) — is the drill even in the language being taught?** Fed an English-heavy source (a phrasebook chapter, a romanization-only textbook page) the author sometimes writes a WHOLE drill in English: *"What does this mean? / Please include some coins in the change."* with that same sentence among the options, spoken aloud by the Cantonese voice. Two checks, both free: **`_off_script`** requires the target-language side (recognition prompt, production/listening/cloze answer, reorder sentence, typed answer, match target) to be in the target script via `tokenizer.script_class` — a deliberate no-op for Latin-script targets, where English and French are indistinguishable by inspection — and a language-agnostic **echo check** drops any drill whose prompt IS its own correct option. Unlike the option guards these run on the ASSEMBLED exercise, which is what lets them vet STORED lessons: `_assemble_drill` is now a thin wrapper (`_build_drill` + `drill_is_sane`), so an all-English lesson leaves no exercises and trips the existing `_AUTHOR_ATTEMPTS` retry, and `main._sanitize_lesson_content` strips unanswerable items from an already-stored lesson on `GET /api/lessons/{id}` **and persists the repair** — the ⚑ regenerate flow addresses stored items by position, so serving a different list than we store would rewrite the wrong drill. `_course_drill_pool` and `_checkpoint_quiz` filter with the same predicate, since they read stored content directly.
  - When these leave fewer than 2 options, the item is **dropped** rather than shipped, per "drills that can't be validated are dropped". The author prompt states both rules too, but a prompt is a request, not a guarantee — these are the backstops. `tests/test_option_hygiene.py` pins them.
  - `_order_tokens_from_sentence` tiles reorder sentences with a longest-first **backtracking** DFS (a greedy walk drops valid drills when a short token shadows a longer one). Cloze `prompt_roman` romanizes around the `___` blank.
- **Untaught-word glosses**: `author_lesson` is passed the `taught` concept registry; for `reorder` drills the model returns an optional `glossary` `[{token, gloss}]` for helper words the learner hasn't been taught (short English, or a POS abbrev like PRT/CL for function words). `_assemble_drill` filters it to `{token: gloss}` for real tiles only; the word-bank renderer shows the gloss as a third line under each tile (jyutping ruby on top, native char, English gloss beneath). **Word-bank grading compares `tile.dataset.tok` (the raw token), never `textContent`** — ruby annotation would otherwise mangle CJK tokens (`你好` → `你nei5好hou2`) and fail every correct answer. Tiles leave a frozen-size empty `.wb-slot` placeholder in the bank when moved (Duolingo-style; no reflow).

A real, hand-written **few-shot golden example** (`examples/lesson_example.json`, deliberately Spanish so it never leaks answers into other targets) is injected into the author prompt — edit it to steer lesson STYLE implicitly. Default model is the cheap reader model; the **admin-only** `lesson_model` setting (and legacy `lesson_premium` fallback) runs the whole pipeline (planner + author) on a stronger Gemini or Claude model to compare quality — see *Pluggable model (A/B)* above.

Stored lesson `content` = `{"segments":[{"teach":{"intro","blocks":[...]}, "exercises":[...drills...]}]}` (one teach→drill segment per micro-lesson; the player still supports multi-segment + end-of-lesson mistake review).

`grammar_lessons.py` (the older per-concept generator that produced a shared `concept_content` artifact) is **no longer called by the lesson route** — only its block/cloze helpers (`_clean_block`, `_conj_cloze`, `_free_cloze`) and `GENERATION_MODEL` are reused by `learning.py`. The `concept_content` table is retained but unused by the new path.

**Faster/implicit vocab:** `_next_batch` packs up to 3 consecutive vocab concepts into one micro-lesson (grammar still taught alone). The author prompt makes teach blocks **proportionate/optional** — straightforward vocab debuts directly in a glossed drill (no dedicated teach block); blocks are reserved for grammar and vocab needing explanation.

**Teach-text reveal (ruby + hybrid translation):** all target-language teach text gets romanization ruby (offline oracle, retroactive on old lessons). English meaning is revealed on hover/tap per word: stored `vocab_glossary` first (free), and for words the lesson never glossed, a `.gl-live` span fetches a live translation on tap via `/api/reader/translate-word` (cached per session). **Inline examples in `prose`/`note` blocks** (e.g. a tones lesson listing `詩·史·試·時·市·事`) are handled by `applyProseRuby`: it walks the rendered text nodes and ruby-annotates only the maximal target-script runs (leaving surrounding English + markdown untouched), so each example char gets its jyutping + meaning. `liveLookup` is forced ON for prose/note (even in foundations) since prose is explanatory teach text, not a graded exercise. The ruby line-height is reserved in CSS (`.tb-prose`/`.teach-target`/table cells at `line-height:2`, `ruby{line-height:1}`) so romanization loading in never re-spaces / jumps the teach text. **Tokenizer note:** the middle-dot family (`·・‧•`) is in `tokenizer._INLINE_PUNCT` so syllable lists split into individual characters, and `romanize_words` (yue) romanizes each word on its own (a batched join re-segments `詩史試…` into chunks that drop single-char readings). This is **AI-lesson teach only** — gated by `_liveLookupOn()` (`player.theme !== 'foundations'`) and never applied to exercise prompts (would leak answers) or the foundations reading track (romanization is the lesson there). `db.get_lesson` / `_lesson_response` expose the unit `theme` so the player can tell foundations apart.

**Word glossing (`vocab_glossary`):** `assemble_lesson` builds `content.vocab_glossary = {native_word: English}` = the LLM's gloss of **every** word used in the teach text (the author prompt asks it to gloss everything — content + function words) + the concepts introduced now (concept label wins on conflict). **No known/unknown filtering** — glosses are hidden by default, so completeness is free. Client-side (`learn.html`): `_tokensToHtml` wraps each glossed token in an **inline** `.gl` span whose English is revealed on hover/tap-focus (a CSS `::after` tooltip) — keeps text flowing inline (the old always-visible stacked label broke layout) and avoids visual over-glossing. **Glossing is teach-only**: `applyRuby(container, glossary)` is passed the glossary at the two teach call sites but NOT for exercise prompts (`renderExercise` calls `applyRuby(root)` with no glossary), so a recognition prompt never reveals its own answer. Word-bank reorder tiles keep their own focused `.tile-gloss` from the per-drill `glossary` field (helper words only) — they are NOT auto-filled from `vocab_glossary`.

NOT yet built (deferred): first-class up-front **unit rows** with a visible roadmap (units still close reactively via `close_unit`); more tenses/languages; error-correction drills. (SRS-deck enrichment and the tutor chatbot have shipped — see below.)

### Tutor chat (`tutor.py`, `static/tutor.html`)

`/tutor` — reached through the unified **Chat** tab: `/messages` pins a **"Language Tutor · AI"** contact row (brand-tinted, above friend conversations) that links here, and the tutor page has no bottom tab bar (fixed-viewport chat) — a **back arrow** in its top bar returns to `/messages`. Free conversation with an AI tutor in the target language (`TUTOR_MODEL = "gemini-2.5-flash"`). One **single-prompt** LLM call per learner message (`tutor.respond`), with the last 20 turns serialized into the prompt (no SDK chat sessions — consistent with `translation._call`). Metered like translate: `_resolve_gemini(user)` charges 1 usage unit per message; rate-limited `20/minute;400/day`.

- **Knows what the learner knows:** prompt context = known SRS words (`db.get_known_words`), the course concept registry (`_registry_block` reuse), weak deck words, and the `learner_profile` setting. Persona: reply mostly in the target language calibrated to those lists, English sparingly; answer MEANING first, then correct; encourage circumlocution, then teach the proper expression with examples / related words / etymology.
- **English = a request for words (enforced):** when the learner drops into English for something they can't say yet (a whole sentence, a slipped-in word, or an explicit "how do you say…?"), the prompt REQUIRES the tutor to return the natural target rendering(s) — 1–3 idiomatic options with a register note each — as `new_items`, **exempt** from the otherwise-strict "be selective, ≤2" cap on volunteered suggestions (`MAX_NEW_ITEMS` is 4 to give the options headroom). The `_already_has` filter still drops options the learner already used/knows, but English message text won't match a target suggestion so asked-for phrases survive. Each option is an Add-to-deck chip.
- **Constructions over fixes:** corrections carry a `construction` field naming the underlying form (e.g. "comparative with 過", "-er present tense"); `explanation` states the RULE, not just the instance. Rendered as a grammar-purple **📐 <construction>** pill on the correction card (`.corr-form`). When a correction (or a just-taught pattern) exposes a generalizable construction, the tutor sets `drill` to that same label, surfacing the 🎯 Drill button to practice it.
- **Target-language-only reply + on-demand translation:** the `reply` is written **entirely** in the target language (English lives only in the structured fields). The same call returns `reply_en` (full sentence translation) and `gloss` ({native_word: English}, word-for-word) so the client offers reader-style reveal at no extra cost: jyutping ruby + **per-word English on tap (`.gl` tooltip shows the English gloss ONLY** — romanization already lives in the ruby, so no redundant second way to see it) + a per-bubble **"Aa"** toggle for the whole-sentence English. The prompt is tuned to be an engaging partner — open-ended questions (almost never yes/no), personality, cultural tidbits, pushing the learner to say more.
- **Drill mode (conditional, no visible prompt):** the tutor sets a `drill` field (a short skill label) ONLY when a reply just taught a **generalizable** pattern (if…then…, -er conjugation, comparatives…) — that's the sole trigger for the per-bubble **🎯 Drill: <skill>** button. Tapping it calls a dedicated endpoint `POST /api/tutor/conversations/{id}/drill` (`tutor.start_drill` / `build_drill_prompt`) that stores **only** a tutor message (the opening drill question) — the learner never sees a "drill me" instruction in the chat. The learner then just answers; the tutor's own drill question keeps the model in drill mode (the main prompt's DRILL-MODE clause judges the attempt via `corrections`, poses the next phrase **built from words the learner already knows** — varying vocab across the deck/known list, exercising the SAME construction — for **3–4 examples** then a recap). The English phrase-to-translate is the one allowed exception to the no-English-in-reply rule. **Vocab strategy is tiered by deck size** (`main.tutor_drill` via `db.count_known_words`), so embeddings are a *large-deck fallback*, not an always-on cost:
  - **Small deck (≤ `tutor.SMALL_DECK_MAX` = 150):** hand the model the WHOLE known-words list and run a single opener call — **no embeddings**. The model builds the drill straight from the list.
  - **Large deck (> 150) — verify-then-snap:** don't flood the prompt, and treat embeddings as a *fallback*. `start_drill` runs ONE cheap opener with a ~`LARGE_DECK_SAMPLE` (40) strongest-first sample + the CEFR profile + total count (no embeddings), and asks it for `expected_words` (the answer's content words). Those are verified by cheap string membership against the FULL known set (`known_word_strings`). If they're all familiar → done, **zero embeddings** (the common case). Only on a miss do we lazily embed the deck via `known_vectors_provider` (→ `main._known_word_vectors`, shared `embedding_cache`, `gemini-embedding-001`, embed only cache-misses up to `LARGE_DECK_VECTOR_CAP` = 1500), snap the unknown answer-words to known substitutes (`_snap_misses`, cosine ≥ `SNAP_THRESHOLD` 0.62), and **regenerate** the opener with a `palette` of substitutes + an `avoid` list. Best-effort: any embedding failure keeps the cheap opener. Cost: 1 LLM call + 0 embeddings on success; 2 LLM calls + 1 embedding on a verify-miss. Metered as 1 unit.
  - **CEFR profile (large decks):** the prompt also carries a compact CEFR spread of the learner's known words (e.g. "A1:40, A2:22, B1:9") so the model can pitch vocabulary even though it only sees a sample. CEFR is already assigned at translation time (`cards.cefr_level`); `db.get_known_cefr_distribution` aggregates the KNOWN-word subset per language, and `main._known_cefr_stats` lazily backfills cards added via lesson/tutor/starter paths (which skip translation's CEFR) using `cefr.tag` (cheap LLM, bounded ≤60/call, persisted on the card so it converges). **(Per-card embeddings:** `translation.get_embedding` now delegates to `embeddings.embed` (`gemini-embedding-001`, 768-dim) — one embedding code path — so per-card embeddings (`cards.embedding`) and `GET /api/labels/suggest-cards` work again (previously the dead `text-embedding-004` silently returned None). Pre-existing cards predate working embeddings, so `suggest-cards` lazily backfills a bounded batch of NULL-embedding cards per call via `main._backfill_card_embeddings` → `db.get_cards_missing_embedding`; the deck converges over a few requests.)
  - **Inline lesson construction-drill (shipped):** the construction drill is also a **lesson exercise type** (`construction_drill`). `learning.assemble_lesson` auto-appends one per NEW grammar concept (after the deterministic drills), using the concept label as the construction. The lesson player special-cases it in `renderExercise` (hides the standard Check/Continue button; the widget self-manages a 4-turn translate-the-phrase loop with its own submit, then calls `onDone`→`advanceExercise`). Via the stateless `POST /api/lesson/drill` (`tutor.run_lesson_drill`). **Target-first planning + liberal LLM judging:** the PLAN call generates target-language sentences that USE the construction, then back-translates each to English (`plan_items: [{english, target}]`). The `target` is a reference example — NOT a match oracle. Judging is ALWAYS a single LLM call (no deterministic string-match layer — that old approach poisoned the judge with slash-alternatives from the plan and caused false rejections). The judge prompt grades from the English meaning alone: ANY valid translation is accepted, even if it doesn't use the construction. When the answer is correct but skips the construction, the judge returns an `alt` (a version that does use it) + a note, shown as a "Using <construction>" tip — so the learner always sees the target form without being penalized. Same-answer override: if the LLM says wrong but the corrected form matches the learner's answer after normalization, it's overridden to correct. If the LLM call fails (API error, bad parse), `feedback` is `None` — the client shows "Couldn't check this one" and the user taps Next to skip (not falsely accepted or falsely rejected). Romanization on corrected/alt forms via the offline oracle. 1 metered call per turn. Formative — completion counts as a correct first-pass. **UX: always tap to advance** — no auto-advance timers; the user reads feedback at their own pace and taps "Next" to continue. Runs on **`tutor.TUTOR_MODEL`** (gemini-2.5-flash) — upgraded from flash-lite which was too weak for reliable grading.
- **Structured side-channel, strictly normalized** (`tutor._normalize` — same trust model as lessons): `{reply, reply_en, gloss≤40, corrections≤3, new_items≤3, points≤3, drill≤60}`. `respond`/`start_drill` share `tutor._run` (call → parse-with-one-retry → normalize → never hard-fail). Filter-then-clip (malformed entries don't consume slots), point values clamped 1–3, `romanization` on every new_item **recomputed by `tokenizer.romanize_text`** (never the model). **`new_items` are dropped if the learner already used the word in their message or has it in their deck** (`_strip_for_match` against `user_msg` + known words) — they earn points for those instead. The prompt makes `new_items` **very selective** (≤2, empty is normal; only high-frequency words central to the exchange — no proper nouns / niche words / words that merely appeared) to stop low-value deck suggestions. JSON-parse failure retries once, then degrades to a plain-text reply — chat never hard-fails on the side-channel.
- **UI (ChatGPT-style mobile chat):** current-chat button opens a left **conversations drawer** (new/delete, ellipsis-truncated; first message becomes the title). the **thread is the only scroller**, the composer stays pinned. The mobile-keyboard handling is the **MDN `visualViewport` pattern** and is fiddly — three interlocking pieces, all required:
  1. **`body { position: fixed }`** + a `visualViewport` handler (resize **and** scroll) that sets `body.style.height = vv.height` so the flex column **compresses above the keyboard** (iOS never resizes the layout viewport itself).
  2. **Follow `vv.offsetTop` via `body.style.top`** (NOT `transform`, which would re-anchor the fixed drawer/tooltip/toast). When iOS scrolls the layout viewport to reveal the focused input, a fixed body pinned at `top:0` gets dragged off-screen and the composer "shoots to the top" — tracking offsetTop moves the body *with* the visible area. We follow iOS rather than `scrollTo`-fighting it, which is also why there's no per-keystroke flash (the old `scrollTo(0,0)` did fight it).
  3. **Override the global `body { min-height: 100dvh }` with `min-height: 0`** — `dvh` does NOT shrink for the keyboard, so the floor would otherwise pin the body at full height and the height-sync could never compress the chat (symptom: page scrolls, composer ends up under the keyboard).
  A `body.kb-open` class (toggled when the visible viewport is >100 px shorter than the layout viewport) zeroes the composer's `env(safe-area-inset-bottom)` padding so it sits snug on the keyboard instead of floating a home-indicator gap above it. A global `touchmove` listener (`{ passive: false }`) `preventDefault`s everywhere EXCEPT real scrollers (`.thread`, `.chats-list`) and the composer when it actually overflows — without it, iOS's document **rubber-band** bounces the fixed page on a drag and reveals empty space below the composer (`overscroll-behavior` alone doesn't stop document overscroll on iOS Safari). The composer textarea auto-grows from one line (44 px) to a cap relative to `visualViewport.height` (~22%, so it shrinks when the keyboard is up) — note it must set `min-height: 0` to override the global `textarea { min-height: 120px }`, else `scrollHeight` is floored at 120 px and the box can never shrink back to one line. Each tutor bubble has an icon-only tools row: **🔊 listen**, **Aa** whole-sentence English, **あ** per-bubble ruby toggle (reader-style, strike-through when off; default persisted in `tutor_ruby_inline`), and **🎯 Drill** (only when `drill` is set). **Corrections render right-aligned UNDER the learner's own message** (a `.corr-wrap` sibling inserted after the user bubble — a correction is about what they said, not the tutor's reply). The collapsed toggle is a **compact amber pill** that hugs the right edge directly beneath the learner's bubble (`.corr-wrap .xtra-head` overrides the generic full-width `.xtra-head` whose `margin-left:auto` chevron would otherwise strand the label on the far left, opposite the right-aligned message); expanding it drops the correction card full-width below. New-word suggestions are a collapsible section in the tutor bubble; fresh messages start open, history loads collapsed. New-item chips have one-click **Add to deck** (`POST /api/cards`, deduped via `/api/cards/status`) AND a **✕ dismiss**. Point toasts bump the ⭐ header total; 402/429 render as inline system bubbles.
- **Fast load / no chat interleaving:** `GET /api/tutor/conversations` returns the newest conversation's messages inline (`latest`) so the page renders in **one** round trip. All ruby for a render is fetched in **one** `POST /api/ruby/batch` call (was N per-bubble `GET /api/ruby`); tokenization runs in a thread. `openConversation`/`send` use a generation guard (`_openGen` + per-send `convAtSend` check) so quickly switching chats can't interleave two conversations' messages into the thread. **Auto-play TTS was removed** (it blocked rendering and didn't reliably play) — listen is on-demand per bubble. The ruby/tooltip/gloss helpers are still copied from learn.html (a shared-file refactor is a known follow-up).
- **Persistence:** tutor turns are stored as their JSON payload in `tutor_messages`; points appended to `points_ledger` per award. Each tutor turn also calls `db.record_study_activity` so chatting keeps the 🔥 streak alive. Ruby line-height is reserved on `.bubble-reply` (and correction/new-item word lines) so the あ toggle / ruby loading never re-spaces the bubble.
- **Contextual "ask about this card" pop-over (`tutor.ask_about_card`, `POST /api/tutor/ask`, study page `cards.html`):** an inviting **💬 Ask tutor** pill anchored to the flashcard's bottom-right corner (`.ask-fab`, set apart from the muted flag/edit header icons; hidden during inline edit) opens a floating bottom-sheet chat (`.ask-sheet` — side gutters + `env(safe-area-inset-bottom)` so it clears the phone's rounded corners/home indicator, all corners rounded, max-width 460) seeded with the card the learner is looking at (`target_text`/`source_text`/`romanization`/`notes` + a human SRS-progress string built client-side). Unlike `respond` (conversation practice, reply must be in-target), this is **study help**: the prompt (`build_card_ask_prompt`) writes the EXPLANATION in the **same language the learner asked in** (English by default — the learner is decoding a card, so the reply is NEVER in the target language) with examples in the target script + romanization + glosses. **Fast path:** the card-ask is tuned for latency four ways — (1) `thinking_budget=0` (threaded `ask_about_card`/`stream_card_ask` → `_run`/`_call_stream` → `translation._call`, which builds a `GenerateContentConfig(thinking_config=ThinkingConfig(thinking_budget=0))`) disables the 2.5 model's thinking pass for this low-reasoning Q&A; (2) it runs on **`tutor.TUTOR_MODEL`** (gemini-2.5-flash) for quality (creative explanations, mnemonics) — upgraded from flash-lite which produced shallow/dumb answers; (3) the known-words context is capped at 40 words (vs 150) so the prompt stays small; (4) **streaming** — the pop-over hits `POST /api/tutor/ask/stream` (`tutor.stream_card_ask` → `translation._call_stream`, a thread-bridged async generator over the SDK's blocking stream) which forwards the tutor's prose answer token-by-token as NDJSON `{"type":"delta","text":…}` events, then one `{"type":"final","new_items":…,"card_updates":…}` once the trailing JSON extras are parsed + normalized. The **streaming prompt format** (`build_card_ask_prompt(streaming=True)`) is: prose answer FIRST, then the `STREAM_META` (`<<<META>>>`) marker, then a JSON object of the extras — so the prose streams live and the JSON is buffered/parsed server-side. **Robust to weak-model drift:** flash-lite doesn't always emit the marker (it may print the structured part as visible `new_items:` / `card_updates:` labels), so the prose/meta **boundary detector also stops at those bare label tokens** (not just the marker), and `_extract_card_ask_extras` tolerates marker+JSON, bare-JSON, or labelled-block shapes; a leading `{` triggers a whole-output JSON buffer whose `reply` is emitted as one delta. The `final` event carries a **cleaned `reply`** (label junk stripped) that the client uses to replace the streamed text, so meta never lingers in the bubble. `final`'s new_items/card_updates still go through `_normalize` (oracle romanization, additive-notes logic). `_prepare_card_ask` shares setup between the streaming route and the blocking `POST /api/tutor/ask` (kept as a fallback); both meter 1 unit up front. **Ephemeral** — nothing is stored; short follow-ups live client-side and are passed back in `history`. 1 metered call/turn; records study activity. Reuses `_run`/`_normalize`, so `new_items` get oracle romanization + dedup-against-deck for free (corrections/points/drill come back empty — the prompt only asks for `reply` + `new_items`). New-item chips have one-click ＋Add (`POST /api/cards`). **Card update suggestions (additive notes):** the tutor can return an optional `card_updates` object (`{notes_append, notes, romanization, source_text}` — only changed fields). **Notes are additive by default**: the prompt asks for `notes_append` (a snippet ADDED to the existing notes); full-replacement `notes` is reserved for fixing an actual error in the existing note (`_normalize` drops `notes` if `notes_append` is also present, so the learner's notes are never silently wiped). `_normalize` validates & caps each field; the UI renders a "Suggested card update" panel (labels: "Add to notes" / "Replace notes") with an **Apply to card** button that concatenates `notes_append` onto the card's current notes (or replaces for `notes`), `PUT`s `/api/cards/{id}`, and live-patches the in-memory study queue. The pop-over CSS/JS lives in `cards.html` (a shared-file refactor with the tutor/learn helpers is a known follow-up); the **reader** version (sentence-aware) is still backlog (`IDEAS.md` #45).

- **Flashcard inline editor (study page `cards.html`, `startInlineEdit`):** the review-card pencil opens an inline editor (source/target/romanization/notes + `LabelPicker`). Beyond Save/Cancel it has: a **🔄 Regenerate AI note** button (`regenerateAiFields` → `POST /api/cards/{id}/regenerate` → `translation.regenerate_card_fields`, 1 metered call) that re-authors the notes field (and recomputes romanization via the offline oracle) WITHOUT persisting — it fills the edit fields so the learner reviews and Saves; and a **Delete** button (`deleteInlineCard` → `DELETE /api/cards/{id}`) that removes the card from the deck, drops all its queued faces, and advances to the next card.

### Foundations — the reading track (non-Latin scripts)

`foundations.py` teaches the writing/sound SYSTEM (script literacy), separate from the AI vocab course. **Fully deterministic — no LLM, ever.** Romanization comes from offline oracles (`korean-romanizer` for Korean; `tokenizer.romanize_text` / indic-transliteration for Hindi/Telugu).

- **Generalizable = data + per-script-type engines.** A declarative track per language (`FOUNDATIONS[lang]` with `script_type` + ordered units of typed lessons). The only script-specific code is the engine, one per `script_type`: **Hangul** (`script_type="alphabetic"`, jamo compose/decompose via codepoint math), **abugida** (`script_type="abugida"`, Devanagari/Telugu/Bengali — already decomposed at the code-point level, composition is concatenation), **tonal** (`script_type="tonal"`, Cantonese/Mandarin — teaches phonological system: tones/initials/finals with listening drills), **simple_alphabet** (`script_type="simple_alphabet"`, Cyrillic/Japanese kana — letter recognition + word reading, no composition math), and **abjad** (`script_type="abjad"`, Arabic/Urdu/Farsi — consonant letter recognition with letter-name metadata, word reading). Adding a same-type language = data only.
- **Tonal lesson types** (`info` / `tones` / `initials` / `finals`): no grapheme tracking. `tones` lessons use curated minimal pairs (e.g. si1–si6 for Cantonese, mā/má/mǎ/mà for Mandarin) with two exercise kinds per pair — "what tone do you hear?" (pick tone name) and "which romanisation matches?" (pick from the minimal set). `initials`/`finals` similarly: hear audio → pick initial symbol or romanisation. All exercises have `hide_roman: True`.
- **`build_units(lang)`** returns ordinary course units with pre-built `content = {segments:[...]}`, reusing the standard lesson player + exercise types (choice/listening/match + `block_build`) plus **gamified mini-games** (`speed_round`, `audio_blitz`, `memory_match`). `block_build` has two compose modes: Hangul jamo math, or `compose:"concat"` for abugida (tap consonant + vowel-sign → concatenate; graded by string equality). Words lessons curate candidates and **filter by decomposition** to those using only letters taught so far. Mini-games are appended as the LAST exercise in each lesson by `_maybe_append_minigame` (called from `_build_lesson_content` after each per-type builder). `_pick_minigame` chooses the type: `speed_round` for grapheme/initial/final lessons (rapid character→sound multiple-choice with a 30s countdown — correct adds time, wrong subtracts), `audio_blitz` for tonal/compound-vowel lessons (hear audio → tap character, per-round timer), `memory_match` for word lessons (flip-card concentration matching word↔meaning or letter↔sound). All three are self-managed exercises (own timer/UI, like `construction_drill`) that directly manipulate `player.combo`/`player.xp` and call `bumpCombo()`; formative (always count as "passed").
- **Romanization is never shown inline in foundations exercises** — it's the very thing being tested, so it would be a spoiler. Every foundations exercise sets **`hide_roman: True`**; the player's `applyRuby(root, null, ex.hide_roman)` tucks romanization into the hover/tap `.gl` tooltip (combined with any gloss as "rom · meaning") instead of rendering ruby. TEACH blocks still show romanization openly. Applies to all foundations languages (ko/hi/te/yue/cmn).
- **Telugu vowel audio workaround:** the Telugu neural voice barely articulates a BARE independent vowel (≈ −40 dB, effectively silent) while consonants/syllables are fine. `_TE_VOWELS` therefore set `audio = symbol + visarga (ః)` — a soft /h/ release that makes the clip audible (≈ −5 dB) while staying essentially the pure vowel. Only the spoken `audio` changes; the displayed letter + romanization are untouched. Hindi vowels synthesize fine and are left alone.
- **Wiring:** `main.create_course` calls `db.seed_foundation_units` for any language with a track, persisting the units as **closed** `course_units` rows (`theme='foundations'`) at the front. They register **no** vocab concepts (so the AI course still starts from an empty registry). **Skippable** — `get_course` marks all foundations lessons `available` (any order), while AI vocab lessons keep strict sequential locking among themselves, independent of foundations progress. Frontend labels the track "📖 Reading · optional".
- Tracks today: **Korean** (Hangul), **Hindi** + **Telugu** + **Bengali** (abugida), **Cantonese** + **Mandarin** + **Thai** (tonal), **Russian** + **Ukrainian** + **Greek** (simple_alphabet), **Japanese** (hiragana + katakana, simple_alphabet — 6 units, 25 lessons), **Arabic** + **Urdu** + **Farsi** + **Hebrew** (abjad).

### Multi-language support

`translation.LANG_INFO` is the language registry — maps codes to per-language config (name, flag, script, romanization scheme, frequency scale, Gemini prompt rules). Supported: `yue cmn` (Chinese), `ja` (Japanese), `fr es de it pt tl ms id sw vi tr nl pl sv nb ro ga` (Latin), `ko` (Hangul), `hi` (Devanagari), `te` (Telugu), `bn` (Bengali), `ur ar fa` (Arabic script), `ru uk` (Cyrillic), `el` (Greek), `th` (Thai), `he` (Hebrew). `/api/languages` derives the frontend language list from it, so the settings dropdown, language pill, and onboarding update automatically.

**Adding a Latin-script language** = an entry in `LANG_INFO` + a voice in `audio.VOICES`. That's it.

`audio.locale_for(lang)` derives the **BCP-47 tag** for the browser's speech recogniser from that same voice name (`zh-HK-HiuMaanNeural` → `zh-HK`), exposed as `speech_lang` on `/api/languages` — so speaking drills need no second table either. An unknown language returns `""` (and gets no speaking drill) rather than falling back to Cantonese, which would transcribe into the wrong language entirely.

**Adding a non-Latin script** also requires:
- `translation.SCRIPT_BY_LANG[code] = "<family>"` (machine script key; default `"latin"`). Exposed as `script_family` in `/api/languages`.
- `tokenizer.py`: if space-delimited, add the script's Unicode ranges to `_ALPHA` (mind combining marks and which punctuation must stay separate); if no spaces (Thai/CJK), add a dictionary-segmentation branch in `tokenize`. Add an offline romanizer branch in `romanize_words` for reader ruby.
- Frontend font: a `--<family>-font` CSS var + `.script-<family>` rule in `style.css`, the Google-Fonts `<link>` in the 4 rendering pages (cards/reader/index/welcome), and add the family to the `script-*` reset lists in the `applyScript` helpers + the inline-edit/onboarding font maps.

The `logographic` flag (`romanization is not None`) controls *whether a romanization face is shown*; the **`--script-font` CSS variable** (set via a `script-<family>` container class) controls *which font renders* — these are decoupled. Never reintroduce a hardcoded `.is-chinese` font assumption for non-CJK scripts.

### Multi-user isolation

Every `db.py` function filters by `user_id`. Admin bootstrap (`db.bootstrap_admin`) migrates any legacy single-user data to the configured admin username on first run.

## Performance conventions

- **Fingerprinted static assets are immutable**: `static_cache_middleware` sends `Cache-Control: public, max-age=31536000, immutable` for `/static/*?v=…` (the `_html` fingerprinting guarantees a new URL per deploy) and 1 h for un-fingerprinted files. Don't serve mutable content from `/static` without a `?v=`.
- **A page's JS/CSS lives in `static/pages/<page>.js|css`, never inline.** The HTML documents are served `Cache-Control: no-cache` (so they always pick up current asset URLs), which means anything inline in them is re-sent on **every navigation**. `/learn` was shipping 82 KB gzipped per page view that way, none of it changing between deploys; it is now 7 KB. `_html` fingerprints these by pattern (`_PAGE_ASSET_RE`), not by a hand-maintained list, so a new page is versioned automatically — and `_compute_asset_version` already walks `static/` recursively, so the files feed the hash. The **theme pre-paint snippet stays inline** (an external file could let the page paint first and flash the wrong theme); so does anything containing a `{{PLACEHOLDER}}` (`register.html`'s Turnstile key), since `_html` substitutes into it. A page with more than one block keeps them as separate files in order (`cards.js`, `cards.2.js`) — concatenating two classic scripts would merge their top-level scopes. `tests/test_page_assets.py` enforces all of this. *Known follow-up:* `?v=` is the global `ASSET_VERSION`, so any static change re-busts every page; per-file hashes would scope that.
- **Fonts load via `<link>` injected by `_html`** (preconnect + stylesheet, ahead of style.css) — never `@import` inside a stylesheet, which serializes CSS → font-CSS → font files on every navigation.
- **Nav data is stale-while-revalidated** (`navSWR` in the nav script, sessionStorage `nav:*` keys): `/api/me` 5 min, `/api/cards/due-count` + `/api/streak` 60 s, `/api/languages` 24 h keyed by asset version, `/api/settings` 60 s (lang widget). Cached values render instantly; a page navigation inside the TTL fires zero nav requests. Invalidation: `renderHeaderStats` rewrites `nav:streak` whenever a page pushes fresh numbers; `applyLang` drops `nav:settings`/`nav:due`; `doLogout` and the login page clear all `nav:*` (a new user in the same tab must not inherit cached state).
- **A mutation that changes cached shell state must write through to the snapshot.** `static/app-shell.js` answers `/api/me`, `/api/settings`, `/api/streak`, `/api/cards/due-count`, `/api/billing/status` and `/api/notifications/counts` from one `/api/bootstrap` payload held in **sessionStorage**, which OUTLIVES a page load. `CantoShell.invalidate(key)` only marks the in-memory `dirty` set, which is rebuilt on every navigation — so it cannot carry a mutation across a page. Use **`CantoShell.patch(key, partial)`** (writes through to the snapshot) or add the route to `markDirtyForMutation`. This is what the onboarding tour got wrong: `POST /api/tour-seen` persisted `tour_seen` server-side, but the cached `settings.tour_seen` stayed stale, so the "What's new" popup replayed on **every** navigation for the whole tab session. `tour.js` now patches the snapshot in `markSeen()` (and guards against a duplicate POST).
- **Audio declares an audio session, and the default is BEING HEARD.** iOS treats a page playing an `<audio>` element as exclusive playback, so a clip pauses the learner's music. The Audio Session API can mix instead — but the choice is a real trade-off, not a free win: `'playback'` stops other audio and is never silenced, while **both** mixing types (`'transient'`, `'ambient'`) are silenced completely by the iPhone's Ring/Silent switch. There is no type that mixes AND ignores the switch. `applyAudioSession` in `static/app-shell.js` therefore sets `'playback'` unless the **`audio_mix`** setting is explicitly `true` (default **off**, both in `main.get_settings` and in the client fallback — `tests/test_audio_session.py` pins that they agree). This shipped the other way round once, on the mistaken belief that only `'ambient'` gave up audio to the mute switch: every learner with their phone on silent got a totally mute app — clips fetched, elements reported playing, nothing came out, on every screen — which is a far worse failure than interrupting a podcast. The Settings row and the 🔊 Test hint both say the ring switch mutes the mixing mode. Safari-only (default since 16.4); Android Chrome takes audio focus with no web API to prevent it.
- **Volume is a gain graph fed by DECODED BYTES, never `createMediaElementSource`.** How hard `'transient'` ducks the user's music is the OS's call and there is no web API to duck harder, so the only lever is our own level — and an `<audio>` element's `volume` can't provide it (it only attenuates, and iOS ignores it). The **`audio_volume`** setting (0.5–3×, `main._audio_volume` clamps; Settings has a slider + a 🔊 Test button that plays a real phrase in the target language) is applied by **`CantoShell.playBoosted(url, onended)`**: fetch → `decodeAudioData` → `AudioBufferSourceNode` → `GainNode` → `DynamicsCompressor` (a limiter — at 2–3× a TTS clip clips into static) → destination. **Capturing the `<audio>` element instead is the trap**: it is the obvious implementation, it is PERMANENT (an element can never be un-captured), and on iOS Safari the element's sound leaves the default output and frequently never arrives — the clip is silent while every check says the graph is healthy (context running, element playing, nothing thrown). That shipped once and read as "I turned the volume up and now hear nothing". Decoding leaves the element untouched, so **every** failure path — 1× volume, no Web Audio, a suspended context, a fetch or decode error — returns `null` or rejects and the caller plays the clip natively: unboosted, but audible. Call sites therefore look like `try { b = CantoShell.playBoosted(url, onended); } catch {}` then `if (b) { b.catch(fallback); return; }`. `stopBoosted()` silences the current source (`stopTTS` and `stopAudio` call it). `keepAudioRunning` installs the gesture listeners (iOS needs one for the first resume) plus a `statechange` watcher, but deliberately does NOT hold the context running — see the next bullet. The reader still plays natively (its clips are already blobs in hand) — see IDEAS.
- **A running AudioContext holds the audio session even in silence, so ours sleeps.** This is the second half of "some sounds still pause my music": not the clip, the *context* behind it. Under `'playback'` a live context keeps the learner's music paused; under `'transient'` it keeps it ducked — and neither ends when the sound does. So the shell wakes the context around playback and suspends it after `AUDIO_IDLE_MS`=2.5 s of nothing (`wakeAudio`/`releaseAudio`/`_busy`), which is what actually hands the session back. Consequences to keep in step: `keepAudioRunning`'s gesture handler wakes and immediately releases (it unlocks, it does not pin); its `statechange` watcher resumes ONLY when `_busy && !_asleep`, or it would fight our own suspend and win; `playBoosted` treats a context WE suspended as fine (wake and play — falling back to native there would silently drop the boost after every quiet moment) while any other suspension still hands the clip back; and every wake has exactly one matching release, including `stopBoosted` (which suppresses `onended`) and a belt-and-braces timer, since `onended` never fires for a node whose stop time never arrives. **`ensureAudioSession()` re-declares the type before we make a sound and on `visibilitychange`** — the type was previously set once, after `/api/bootstrap` returned, so on a cold load the first clip could play under the UA default, and iOS resets the category after an interruption anyway. `tests/test_audio_session.py` pins the whole lifecycle.
- **Sound effects are their own bus with their own setting.** `CantoShell.tone({freq,start,dur,type,vol})` synthesizes the ✔/✘/streak/complete chimes on `_sfxNode` → limiter → destination, scaled by **`sfx_volume`** (0–2, `main._sfx_volume`; **0 = off**, the one audio in the app that is genuinely optional — speech clamps to a floor of 0.5 instead). Two settings because they pull in opposite directions: the words are what a learner turns UP over music, the beeps are what they turn DOWN, and one slider could only split the difference. Effects skip the speech `_gainNode` entirely. **The tones must be synthesized by the shell, not by the page** — `learn.js` used to build its own `AudioContext` for beeps and never suspend it, which is precisely how the first ✔ of a lesson took the audio session and kept it for the life of the page; `tests/test_audio_session.py` asserts no page creates an `AudioContext` of its own.
- **A failed audio element must never be cached, and `play()` always needs a `.catch`.** An `<audio>` whose fetch errored is permanently dead — every later `play()` on it rejects. `learn.js`'s `_prewarmTTS` used to cache the element unconditionally, so ONE transient `/api/tts` failure silenced that clip for the whole session while every other clip worked, and `playTTS`'s bare `.catch(() => {})` hid it: the "audio randomly doesn't play" bug. `_makeTTSAudio` now attaches an `error` listener that evicts the entry, `playTTS` rebuilds an element with `.error` set and retries once (skipping the retry for `NotAllowedError`, which is the autoplay policy, not a broken clip), and prewarming is throttled to `TTS_PREWARM_CONCURRENCY`=3 — `_prefetchLesson` asks for every clip in a lesson at once, and each is a separate edge-tts websocket on the server, so the unbounded burst was itself provoking the throttling. Any bare `.play()` also leaves a play/pause button stuck in its `.playing` state, since `onended` never fires. `tests/test_tts_playback.py` runs the real functions out of `learn.js` under node.
- **A clip that can't be fetched must LOOK dead, and a drill that needs it must be dropped.** `learn.js` tracks per-clip health (`_ttsHealth`: `ok`/`fail`, plus watchers pruned by an `alive()` check). `bindAudioBtn(btn, text, lang)` — the one way a 🔊 button is wired — paints THREE states, because "I tapped the speaker and nothing happened" is the complaint it answers: not fetched yet (`.audio-loading`, disabled, a slow pulse — bounded by `AUDIO_READY_TIMEOUT_MS`=6 s so a clip whose `loadeddata` never arrives can still be tapped), ready (normal), and failed (`.audio-dead`, disabled, restored if a later fetch works); `cards.js`'s `playCardAudio` does the same after its own retry (`.audio-btn.audio-dead` lives in `style.css`, `.audio-play.audio-dead` in `learn.css`). A live-looking control that silently does nothing reads as the app being broken. **`_audioOnly(ex)`** marks the drills whose question exists ONLY in the sound — `listening`, `audio_blitz`, sound-mode `memory_match`, and any drill with `audio` and no readable prompt (foundations tone/`block_build` drills) — and `_guardAudioExercise` (called at the top of `renderExercise`, and again from a watcher if the clip dies while the drill is on screen but before it's answered) gives the clip ONE `_retryTTS` and then `_skipExercise`s it. A skipped drill shrinks `player.total` + `segTotals[segIdx]` (`_dropFromTotals`), so it never counts against the score and never strands the progress bar short of 100%. `_maybeListeningVariant` also stops MAKING ear-only drills once audio is evidently down (`_ttsFailCount > 0 && _ttsOkCount === 0`). `show()` calls **`stopTTS()`** whenever the player leaves the teach/exercise screens, so a prompt never follows the learner out to the course map or the results screen. `tests/test_speaking_drills.py` pins all of it.
- **Pollers pause when the tab is hidden** (`document.hidden` guard): notif counts (60 s, everywhere), messages conversation poll (5 s), cards due-poller (30 s). Any new `setInterval` that talks to the network must do the same — Safari's energy diagnostics flag background polling.

## Code Conventions

- All DB access goes through `db.py`.
- **Open every connection with `db.connect()`**, never `aiosqlite.connect(DB_PATH)` directly. `foreign_keys` and `synchronous` are per-CONNECTION pragmas (unlike `journal_mode = WAL`, which lives in the DB file header), and SQLite defaults `foreign_keys` to **OFF**. Because this module opens a fresh connection per call, setting the pragma in `init()` armed only `init()` — every `ON DELETE CASCADE` in the schema was inert everywhere else, and `delete_shared_deck` leaked its `shared_deck_items` / `deck_imports` / `deck_ratings` / `deck_import_cards` rows permanently. The helper sets both pragmas so the schema's cascades are load-bearing. `init()` keeps a raw connection on purpose, so migrations (012 drops and recreates tables) behave exactly as before. `tests/test_fk_cascades.py` pins this.
- **Migrations** live in `migrations/`, are applied in filename order, once each (recorded in `schema_migrations`). Schema changes are `.sql`. A `.py` file exposing `async def migrate(conn)` is also run, for DATA backfills SQL can't express safely — chiefly anything that reads a value back out of a `json.dumps()` blob, since non-ASCII is `\u`-escaped there and a SQL `instr()` would match ASCII rows while silently missing the rest (see `046_textbook_unit_chapter_disambiguate.py`). Never edit an applied migration — it is a no-op on every DB that already ran it; add the next number instead.
- Keep API responses lean — no fields the frontend doesn't use.
- `srs.py` is pure/stateless — pass state in, get new state back, no side effects.

**Colors & dark mode**  
The visual identity is **"Field Notes"** (from `mockups/`): deep-viridian `--primary`, persimmon `--energy(-soft)` for streak/combo accents, `--gold(-soft)` for XP/crowns text, ink text on a warm bone `--bg`; `--display-font` (Bricolage Grotesque, Google-Fonts `@import` at the top of style.css) styles `h2/h3/.display-font`, body text is Public Sans. **Never hardcode colors** — use the semantic tokens defined in `:root` in `style.css` (`--primary-soft`, `--good-soft/-strong`, `--warn-soft/-border/-accent/-strong`, `--danger/-soft/-strong`, `--grammar-*`, `--neutral-*`, `--surface-alt`, `--reader-known/-weak`, `--overlay`, `--tooltip-bg`, `--on-primary`, `--shadow-pop`, …). Dark values live in the single `[data-theme="dark"]` block; adding a new color means adding it to BOTH. Theme selection: an inline pre-paint snippet in every page's `<head>` resolves `localStorage.theme` (`auto` → `prefers-color-scheme`) and sets `data-theme` on `<html>` before first paint; `/static/theme.js` handles live OS changes + the `theme-color` meta; Settings has the Auto/Light/Dark segmented control. New pages MUST include the snippet + `theme.js` + the `theme-color` meta. Tooltips/toasts with white text use `--tooltip-bg`, never `var(--text)` as a background. Decorative constants (confetti, CEFR badge scale) are deliberately not tokenized.

**Shadows**  
Use `var(--shadow)` for card/surface elevation and `var(--shadow-pop)` for floating dropdowns/modals. Avoid hardcoded `box-shadow` values — both tokens have dark-theme variants.
